# GoFurry D3-A3 — itch.io Source Feasibility & Minimum Multi-Platform Intake

**状态：冻结 / 受限实施契约** · 2026-11-14  
**基线：** GoFurry `e06a3c5f7252b18bc0a1630dda5afc66ae7aa580`、Harvest `349730b5c3ff57be084dfac72dfb77f19dacb54c`（D3-A2-B 双仓 CI 已通过）。  
**目标：** 快速验证 itch.io 可长期支持的官方/公开发现与作品资料来源，并在技术、授权和数据质量均成立时完成**最小**可运行集成；否则记录阻塞，**不得阻塞 D3-B/C 前台和 D4 运营建设**。不再将 A3 拆为 A3-A/B/C。

## 1. 必须核实的外部事实

官方基础资料：
- https://itch.io/docs/api/overview
- https://itch.io/docs/api/serverside
- https://itch.io/updates/rss-feeds-for-browsing-games
- https://itch.io/docs/legal/terms

已知 itch.io 官方公共 RSS 可用于发现新上传游戏、首页精选、活动促销与部分浏览页；并不意味着 feed 涵盖全站、提供稳定内部 ID 或提供完整资料。官方 Server-side API 主要针对已授权账户有权编辑/拥有的游戏，**不是**无授权检索任意第三方游戏的通用 API。测试前核实实际响应、访问政策与能力边界。不得调用非官方逆向接口、绕过限流/登录/robots、用本人的 itch Key 假装拥有他人作品；不得宣称来源许可/元数据范围超出可证事实。

GoFurry 已存在 `game_sources.platform_code='itch_io'`，来源键为规范的 `creator/game`，以及受控的跨平台关系流程；**保留这一身份约束与 D1/D3-A1 的 Game Public ID**。页面 URL 可以变化，不能默默重新生成 Game 公共身份；只有可靠的作品级跨平台证据才自动关联。弱名称匹配不可合并。

## 2. 首先进行有界能力评估

用官方文档、实际允许的少量公开 RSS 和公开页面（如果服务政策允许）判断：
1. **发现：** Feed 覆盖范围、分页、重复/乱序、时间语义、作品 URL、是否存在稳定 item GUID 或标识；验证轮询/重叠窗口/恢复。
2. **资料：** 是否能在允许的公开来源获得 title、纯文本 summary、封面、题材/类型、开发者、发行状态、可获取链接；每个字段记录真实来源及能否复核。
3. **内容等级：** 成人/NSFW 状态是否有可依赖的明确声明；缺失不是 SFW，无法可靠判断则只能候选内部等待证据，不要求每个项目人工复审。
4. **跨平台：** 作品专属 Steam 商店链接或经证实的双向关联、可用于归属同一个 Game 的证据。开发者主页、标题/封面相似不能直接合并。
5. **能力边界：** 价格、销量、下载量、玩家数、新闻等未实际可获得或无权访问的字段，必须明确 **unsupported**；不强行复刻 Steam 数据、不要使用视觉推测生成数字。
6. **运行成本：** 请求频率、失败/阻断率、内容尺寸、缓存/原始文件保存、受控配额、访问风险、未来失效行为。不要将大规模公开抓取当作测试前提。

禁止为了“完成”而把需要帐号授权的自身游戏 API 用成第三方全站聚合。没有可信的公开详情能力，也允许只支持 `itch_io` 官方链接与 RSS 候选；不伪造 `itch.details`。

## 3. 根据评估结果的明确执行分支

**GO — 已验证的允许来源稳定且有实际价值时：**
- 在 Harvest（不是 GoFurry）做最小、类型化、受控的 `itch` RSS discovery capability；仅在确有可验证可用且合规的公开详情时加一个最小 metadata capability。使用固定官方 origin/路径白名单、Robots/访问规则、边界尺寸、已有 Permit/egress/quota/Job，不建第二套爬虫或队列。API Key 无需用则不配置；如果确实需要授权，只为获授权的第一方游戏提供明确隔离路径，不作为公开第三方来源能力。
- GoFurry 通过现有 `GameSource/Intake/Collection` 接入，去重 `creator/game`、RSS GUID/URL，记录真实来源字段和已证实的作品级关系。只有高确定性题材和 SFW 正面证据时允许自动公开，不能为追求通过率牺牲 SFW 边界。
- 原有 Site、Game、Steam 资料、已发布身份、持久快照和人工覆盖优先级不变。原始采集结果不能在 SSR 时实时取；来源过期/不可达不得导致已经正式发布的作品消失。
- 单独的官方 RSS discovery 游标必须能在分页/重复/服务重启后恢复；容量/速率有上限。若 feed 根本不分页就不虚构支持分页，只记录滚动窗口实际可实现的覆盖范围。
- 只改必要的两仓模块、Goose forward migrations 和 CI；不开发完整游戏 UI、泛型 Provider 注册产品、UGC、评论、抽奖、Admin，不修改旧站、steam-go、AI Gateway。

**NO-GO — 公开详情不可稳定、合规、准确取得：**
- 不强行构建不可靠的详情采集器；维持现有多平台官方链接和手工例外纠错能力，允许 RSS 作为轻量候选依据但不冒充自动建档成功。
- 交付证据与阻塞原因，说明接入创作者授权或未来官方接口变更可解决哪些能力。
- 直接结束 A3，继续 D3-B，而不是以“待研究”为由无限期阻塞游戏前端。

## 4. 验收和交付

- 必须同时完成 **能力矩阵**、官方文档依据、最多有界的允许公开测试、成功/失败与数据缺失样本，并明确是否 **GO / NO-GO / RSS-ONLY**。
- 如实现代码，使用真实 Harvest Server/Worker、GoFurry Intake、独立 PG18/Redis 和模拟 itch.io HTTP/RSS，证明重复、分页（若真支持）、阻断、来源重命名、Steam 关联、并发、来源错误、临时不可用、Consumer 重放及 31/181/365 天已公开作品不消失。绝不把所有来源无 adult 标记视为 SFW。
- 两仓分别提交/推送 `develop`，匹配 SHA 的 CI 通过；不修改共享 DB、生产、配置密钥、官方源的大规模内容。
- 验收文档 GoFurry `docs/v0.1-d3-a3-itch-feasibility-acceptance.md`；如改 Harvest，额外提交它自己的简短验收。写明实际完成能力和当前无法承诺的能力，避免虚构工作量及精度。

## 5. 后续主线

A3 不得阻塞后续 **D3-B（游戏首页/目录/搜索/合集）→ D3-C（游戏详情/媒体/动态/趋势）→ D4（统一 Admin + Harvest 运营）→ D5（旧站真实数据迁移与全链路验收）→ D6（CN→INTL 独立数据库内容投影）→ D7（上线前综合验收；暂定阶段名）**。如果为了按期交付，需要先实现 D3-B/C，再补 A3，允许推迟而不反过来重做 Game 身份模型。
