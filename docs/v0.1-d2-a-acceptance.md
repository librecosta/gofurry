# D2-A — Navigation discovery, Heat and editorial

Apply the new `202611120001_navigation.sql` migration explicitly with `task migrate ACTION=up CONFIG=<private-yaml>`. It adds Site classification, reviewed languages and known first publication time; five tables hold moderation history, fixed slots, UTC daily counters and the current Heat ranking and head. It adds no foreign key or cascade and leaves earlier migrations intact. Start, Game, wallpaper, Harvest evidence and Yearbook identities are unchanged. No migration or deployment was performed on shared infrastructure.

Existing D1 publications start as `unreviewed`: only previously public detail and Yearbook URLs retain their prior access until the first review. These rows do not appear in directory, export, recommendations, rankings or statistics. Review cannot guess the first publication time for older records, so they do not enter “recent.” New Sites need a completed SFW review and primary category before publication. CN rejects `mixed` and `adult` decisions; INTL can record them internally but both deployments serve only reviewed SFW content in navigation. Locale and cookies never grant visibility. A new decision supersedes the D1 exception; fresh API and revalidated SSR reads immediately enforce it.

| API | Contract |
| --- | --- |
| `GET /api/v1/sites/discovery` | Three named, nullable `featured` slots, up to eight `trending` and eight `recent` entries, eight category counts and one nullable `random` card. Cards are not repeated across home slices; slot assignment does not affect directory ranking. |
| `GET /api/v1/sites/directory` | `q` (trimmed, 80 Unicode characters), `category`, `tags`, `language`, `locale` (`zh` or `en`), `sort`, `page_size` (default 24, max 48) and `cursor`. Comma-separated codes are OR within a filter, AND across filters. Search is case-insensitive across bilingual names, summaries and controlled tags; punctuation is literal. Blank queries default to `published_desc`; nonblank to `relevance`. Other choices: `name_asc` and `heat_7d`. |
| `GET /api/v1/sites/:publicID/stats` | Seven-day effective view and click aggregates when the sample qualifies. No visitor or raw-event data. |
| `POST /api/v1/sites/:publicID/interactions` | Same-origin JSON of at most 80 bytes, with one `type`: `detail_view` or `outbound_click`. `204` persisted, `202` deduplicated, `429` limited. No public editorial endpoints. |

The eight stable codes are `community`, `gallery`, `literature`, `resources`, `marketplace`, `knowledge`, `gaming`, and `events`. A Site has one primary and up to two distinct supplemental codes. The directory returns the 12 controlled tag labels; Site languages are reviewed independently of translated descriptions. Country and nonprofit/commercial status are not fields or filters. Pages use Public ID to break ties and one PostgreSQL snapshot per response. Restart paging on `400` for a stale cursor, changed filter or removed anchor. Ordinary editorial changes can still move results across pages; pages do not pin a database snapshot across requests. `404` covers unavailable identities; a database outage is `503`.

Use the existing API binary and an explicit private YAML for the correct region. `navigation inspect PUBLIC_ID` shows the revision; `navigation review PUBLIC_ID REVISION --rating sfw --primary community --tags forum --languages en,zh --actor OPERATOR --reason REASON` replaces the audited profile. `navigation features` previews all slots; `navigation set-feature primary REVISION PUBLIC_ID --actor OPERATOR --reason REASON` assigns one, and `-` clears it. Archived or restricted Sites disappear from public slices without deleting their internal assignments. `navigation refresh-heat` requests an immediate refresh under the same PostgreSQL lock as the scheduler.

Heat v1 sums `0.85^d × (views + 3 × clicks)` for UTC days 0–6 in fixed-point integers. A Site needs at least 10 events on at least two dates. Enable the half-hour scheduler explicitly with `navigation.heat_enabled: true`. The ranking and its head publish in one transaction; the aggregate cutoff labels the transaction snapshot, so events still uncommitted at that point can appear on the next run. No snapshot means `cold`; a previous UTC day or a snapshot more than two hours old is `stale`. Both states return an empty trending slice and directory Heat sorting falls back to first publication. No historical totals are imported.

Enable ingestion separately with the existing Redis, an exact `navigation.interaction_origin`, and a private random 32-byte `navigation.interaction_hmac_key` in unpadded base64url. All instances of a deployment must share the same secret and Redis state. The production edge must overwrite the single client IP forwarding header, restrict backend access to its trusted address, and keep the event route out of access and identity-bearing error logs. The Nginx example forwards only the headers ingestion needs. There is no cross-origin permission. On an eligible Site with ingestion enabled, the detail sends one candidate after three visible seconds, excluding prerender. An external link opens natively even when the Beacon fails. The server rejects an unknown field, arbitrary URL, untrusted forwarding or invalid origin. It retains only expiring HMAC keys in Redis and Site/day totals in PostgreSQL. Limits are 1 per Site/IP/type per rolling 30 minutes, 8 per UTC day, 30 attempts per IP/minute and 600 per deployment/minute. Redis or PostgreSQL failure can drop an event; reservations are not retried after an uncertain database write. Counts are not unique humans. Use Redis with `noeviction`; replacement or lost Redis state ends the old deduplication window, so keep ingestion off during an uncoordinated replacement.

### Measured acceptance

Run `task check:catalog` with a built Web. The fixture starts PostgreSQL 18.6 and Redis 8.2.1 in disposable containers and runs both regional APIs and Chromium. The Go fixture exercises fresh and forward/repeated migrations, preserved D1 history, classification, literal bilingual searches, keyset ordering, UTC rollover, both low-sample gates and two independent Redis clients. It checks Heat v1 fixed-point score `1000137569 → 829600000` at UTC rollover and verifies one snapshot publication under concurrent refresh. Eleven browser/API tests cover the fixed slices, same-origin Beacon, native external navigation, SSR and forbidden ingress. The fixture also verifies moderation withdrawal in both regions, Redis fail-closed counting with reads still available, and PostgreSQL outage/recovery without replaying an ambiguous write. A separate Harvest D fixture passed with 22 fixture requests. The [develop workflow](https://github.com/librecosta/gofurry/actions/workflows/check.yml?query=branch%3Adevelop) runs build, sqlc, catalog, Start, HMR, container and collection checks.

Set `NAVIGATION_MEASURE=1` when running the catalog fixture to reproduce the local measurements. Synthetic Sites each have seven active dates. Times are wall-clock except Go user CPU; warm filtered ranking is the mean of 20 reads. “Cold” means no Heat snapshot on the first directory read, not an empty OS/PG buffer cache. Buffer hits are the PostgreSQL database counter delta for the warm sample; there is no application response cache. WAL is the delta for one full refresh. These are single-machine fixture measurements, not service latency targets.
