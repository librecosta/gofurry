## 1. Product boundary

GoFurry has **two** public business entities: Site and Game. Harvest is an independent acquisition engine and authoritative owner of `Target / Schedule / Worker / Permit / Observation / Change Stream`. GoFurry owns curated business entities, public URLs, field precedence, its own compact **long-lived facts** and publication of yearbooks. LibreCosta Admin is a distinct login/audit system, to be connected via authenticated GoFurry management APIs later.

There is **no third user-facing observation portal** and no separate collection service, full HTTP inspection dashboard, general-purpose metrics framework, redis queue, headless crawler, time-series database, generic CMS, arbitrary GoFurry-controlled upstream fetcher or shared cross-database foreign key.

The main invariant: **public Site/Game SSR and listing APIs read only GoFurry's regional PostgreSQL/projection**. They never call Harvest. A Harvest failure never erases editorial content or takes down public Site/Game pages.

Site Yearbook is a **public, per-Site, per-UTC-year** product. A domain move does not change Site identity or yearbook path. Tech weekly may use the same compact evidence later, but a weekly publishing/auto-mail system is out of this contract.

## 2. Region, source identity, security

- D1-B starts with GoFurry **CN's** authorized public/SFW Site/Game records and one approved Harvest namespace/stream. Harvest may be deployed centrally; source data shared with INTL only through future reviewed **CN → INTL content publication projection**. No region-to-region user data copying, direct shared GoFurry DB, or Intl public read-through of CN Harvest.
- Preserve `Site.id`/`Game.id` UUIDv7 and their permanent public IDs from D1-A; do not use Steam AppID or domain as business primary key.
- Site public business URL may include a path/query; Harvest `web.origin` is only an origin (`https://host`) and `web.domain` a DNS hostname. Never treat business link path, unrelated embedded URL or an external redirect as authorization for new crawl targets.
- Steam sources are eligible **only** if `game_sources.platform_code='steam'` and the source is active; each `steam.app` Target is a canonical positive uint32 AppID. Other recorded platforms remain **links only** until their Harvest Providers exist; no fake data.
- All Harvest calls are **server-side**, over the private authenticated connection using only an explicit YAML `harvest` block. No browser access or public proxy endpoint, no credential in JSON responses, log, Swagger, URL query, Task output or DB. Keep source route/egress/quotas in Harvest's PostgreSQL policy; GoFurry must not override source networking policies.
- Provision two narrow service identities: a writer for Target/Job/Schedule and a reader owning the stream Consumer. Operator enrollment is an **explicit one-time setup** on Harvest; the ordinary GoFurry runtime must not hold an administrator/operator token. Disabled/unconfigured integration is an allowed startup state; no auto-migration/credential discovery or env bindings.
- A Collection operator action later comes through the **existing GoFurry Management app**, loopback, verified LibreCosta Admin actor, role and audit; never add unauthenticated public mutation endpoints. B1 may expose **private GoFurry CLI commands** for binding/reconcile/test rather than building a new Admin UI.

## 3. Collection bindings are references, not a second Target Registry

GoFurry owns a minimal durable association between an authorized D1-A Site/Game and Harvest's source Target UUID.

- A Site may have zero/multiple Web Targets (`web.domain`, `web.origin`) and a Game may have zero/multiple Steam or future platform Targets. One Harvest Target can be used by several business entities: **never clone target observations per source just because two sites share the domain**.
- The mapping records the GoFurry owner **as a typed FK** (either site FK or game FK with a CHECK exactly one is set), stable normalized provider/resource/external key used only for reconciliation, Harvest Target UUID if registered, purpose (primary/alternate/domain/steam) and active/effective-from/effective-until attribution period. Old bindings become inactive/closed without losing which Site owned a past observation. A site domain move must not rewrite past fact attribution.
- This limited identity mapping is **not** a second independent site discovery catalog. Do not copy Harvest's Worker, Permit, quota, raw observation and route schemas into GoFurry. You may use a small canonical-source reference row shared by bindings solely to safely deduplicate Target registration; explain why each table exists. No free-floating unowned sources.
- Create/upsert via `POST /api/v1/targets` (`provider/resource_type/external_key/namespace`), save canonical Target id and validate that a subsequent `GET /targets/:id` resolves the expected provider/resource/namespace/external key. The API is idempotent for the same registered source; a mismatched existing Target is an error.
- A desired schedule is explicitly defined by `target + capability + schema + typed params + semantic scope + recurrence`. Deduplicate it across bindings that need an equivalent collection. Persist remote Schedule ID and local intent/status/revision. **Harvest's POST /schedules is not assumed idempotent**; before retry after an unknown outcome, enumerate/check the permitted remote schedules and reconcile instead of duplicating. Use CAS on PATCH. Never archive an externally shared Target or stop a Schedule until no active GoFurry binding requires it; never touch a Target/Schedule not owned by this GoFurry integration.
- Initial schedule examples, not universal automatic contracts: `web.http` daily, `web.dns` daily, `web.tls` low-frequency, `web.robots/sitemap/assets` weekly, `web.rdap` monthly; `steam.details` daily per chosen language+store_country, `steam.news` every 6–12 h selected apps, `steam.players` selected games point-in-time 30–60min. No automatically turning on every capability for every new record. Respect Harvest minimum intervals, shared Storefront rate and official daily budgets. Some B2 resources require Robots and known HTML candidate bindings; do not attempt unavailable dependencies silently.
- No distributed transaction spans GoFurry and Harvest. Write desired local intent first; reconcile over authenticated API; persist confirmed remote identifiers and outcome. Repeat safely on network loss/restart with bounded backoff and version locking. Schedule disabling when editorial content is archived is an explicit reviewed business decision; it does not erase historical site evidence.

## 4. Reliable GoFurry consumer

Follow exactly Harvest's public protocol, not its private SQL:
1. Explicitly enroll the reader-owned consumer on Harvest via operator setup.
2. `POST /consumers/{id}/reset` then staged paged `GET /snapshots/current`; replay paged `GET /changes` from baseline through the published head, respecting stream, capability grants, position and `scope_key`.
3. In a single **GoFurry PostgreSQL transaction**, activate the new projection and persist stream epoch/cursor; only then `POST /consumers/{id}/ack`.
4. Normal polling processes new changes idempotently by `(Target UUID, capability, output schema, scope key, stream position)`, persists new position and own cursor atomically, then ACKs. Lost ACK response is retryable; a 410 expired cursor requires a staged **full current-state reset**.
5. A reset/replay may reconstruct the current state but must **never erase the durable historical fact ledger** or fabricate the observations that were missed during a retention gap. Log/record an explicit coverage gap and recover the latest projection.
6. A Harvest source observation is accepted only when its target binding, namespace, capability, semantic scope and output schema are recognized. Never apply cross-site/game or cross-region observations. Unknown future schema versions cause explicit defer/diagnostic, not interpretation as empty data.
7. Errors/partial/unavailable never override the last-known-good field. Confirmed empty and tombstones are scoped and must be handled by explicit source evidence; no deletion inference from a temporarily smaller Steam News page.
8. Store publisher-controlled Site/Game names, summaries and editorial status in the existing D1-A tables. Source facts live in a **separate typed projection**, not in a field that overwrites manual edits. Game zero players is genuine if success is verified, missing price is not free and a storefront locale is not the egress location.
9. The consumer runs as one small optional background component in the GoFurry Go monolith, **not** a separate deployment. Use PostgreSQL advisory/row-lock single-active claim if several instances are running, bounded batch/page sizes, backoff, clean shutdown and no HTTP request-loop busy polling. The existing Fiber readiness/Start/Wallpapers must remain unaffected when Harvest is unreachable.

**Important Harvest shapes already verified:** `ObservationView` exposes `target_id, capability, output_schema, scope_key, observed_at, received_at, source, evidence, sample, job_id, attempt_id, content_hash`. `CurrentView` items also carry **confirmed_at**; repeating a semantically equal observation refreshes the current confirmation but need not produce a Change Event. `ChangeView` exposes monotonic `position`, `action`, scoped identity and optional observation, with bounded history. Do not invent a stream containing every successful HTTP request.

## 5. Long-lived compact facts and evidence

Harvest defaults to **14 days of Change Stream** and **30 days of retained history/samples**. It is not the long-term source for annual reports. GoFurry's durable facts should be compact, explicitly typed and independently attributable.

Minimum conceptual records (one table can serve multiple narrowly related kinds where clean; no speculative 30-table telemetry framework):
- **Current source projection:** accepted latest normalized HTTP/HTML technology, DNS/TLS, RDAP, chosen Site URL evidence and current Steam details/region price/news/player samples. Key by target+capability+schema+scope. Bound payloads and retention; not a full mirror of Harvest's JSON or HTML.
- **Site fact transitions:** only meaningful changes, keyed by business Site and effective target-binding period, fact type/key, prior/new compact normalized values, evidence provenance, first_observed_at (NOT guaranteed actual deployment time), source observed_at/received_at, Harvest target/observation+scope, ruleset version, and source semantic hash. Persist enough **sanitized minimal evidence** to verify a future yearbook assertion after Harvest prunes the original observation; a pointer+hash alone is not enough after 30 days. Avoid raw HTML, full response bodies, private RDAP contacts, unbounded TXT, DNS TTL jitter, cookies and auth tokens. Content/field-based size limits required.
- **Site coverage daily summary:** per Site/Target/Capability/Scope/UTC day, latest confirmed-at sample, freshness and explicit evidence status; record **whether a supported confirmation was seen that day**, not exact upstream attempt count. An every-day bounded `/observations/current` sweep (or equivalent proven API) can use the returned `confirmed_at` to mark days where at least one confirmation occurred, including unchanged state. A day with no report is **unknown/not recorded**, not a measured outage. If confirmation occurred on dates missed by a periodic sweep, do not backfill days without durable evidence. A separate failure/attempt coverage count would require an explicit, metered upstream status interface, not fabricated counts from Change Stream.
- **Game source facts:** typed price per country+locale, news by source GID, present values and selective bounded point-in-time samples. Do not design permanent Steam minute bars, raw article archives or broad game analytics in D1-B1; keep stable IDs and source provenance for future decisions.

Semantic detection should ignore volatile TLS/session/proxy response fields and low-value nonce/jitter. Site tech transitions explicitly record `ruleset_version`, evidence codes and confidence; **a detector ruleset update is NOT proof that a Site migrated framework/CDN that week**. Unknown/non-detection is not proof of removal. CDN/hosting changes may reflect traffic-region differences; include vantage and distinguish source statement from inference. For DNS records preserve meaningful normalized RRsets without TTL-only transitions.

Keep curated content unchanged. No automatic last-seen-only 'site dead', arbitrary security grade, HTTP/2 adoption rate, or dubious uptime percentage. Use LibreCosta Uptime separately for actual availability if that becomes a requirement.

## 6. Site Yearbook (D1-B2 after facts have been captured)

**Public URL reserved in D1-A:** `/sites/{public_id}/{slug}/yearbook/{year}`, with the same CN/INTL locale prefix rules. Yearbook belongs to Site identity even if its registered domains change; link valid fact events to historical target-binding effective periods.

- Annual statistics use UTC [Jan 1 00:00, next Jan 1 00:00) and are finalized after the year closes with a modest data-arrival grace period (candidate **Jan 8 UTC**). Never invent pre-capture history: if monitoring began November 2026, its 2026 yearbook can at most cover the recorded Nov/Dec period and must state so. If there is too little trustworthy evidence, do not publish an empty yearbook.
- One `(site_id, year)` annual identity, versioned derived snapshot and publication state. The **current canonical slug** is used for URL, not the slug from that year. Derived summary is repeatable from retained compact events+daily coverage+editorial snapshots. Idempotent generation with DB lock/unique key, no double page after restart; run as low-frequency background task within GoFurry API or an explicit scheduled CLI with owned PostgreSQL locking, **not a new yearbook microservice**.
- Initial public sections: Site identity and evidence coverage dates, meaningful domain/redirect changes, confirmed tech stack/CDN evolution, DNS/TLS certificate timeline if material, year-end last-known-good, chronological important changes and **data quality disclosure**. All claims display actual source/ruleset and first-observed time in evidence details where appropriate. `Last observed` never becomes `date upgraded`.
- Report uncertainty honestly. Do not infer a site's stability from a few HTTP samples or equate missing samples with outages. A ruleset version change must not be counted as a site technology migration without corroborating evidence.
- Annual report text uses **deterministic zh/en templates**, not generative claims. If localized editorial text is missing, omit the translation or clearly show its true source language; never pretend bilingual generated truth. AI Gateway may polish future editorial copy under strict sourced facts but is not needed here.
- Real public SSR: 200 only for eligible published yearbooks of published permitted Sites, proper title/description/canonical/hreflang and discoverability through Site detail and sitemap. Missing year/invalid date/unpublished/draft => real 404; GoFurry DB unavailable => 503. No on-demand yearly aggregation during SSR; serve already materialized yearbook from GoFurry DB, cache bounded and invalidate when a reviewed correction is published.
- Corrections use immutable published revision/audit and regenerate/version instead of silently overwriting a signed annual narrative. Site archival versus already published historical yearbooks is a separate reviewed public lifecycle; default no public leakage.
- Optional **Tech Weekly** can later select material high-confidence changes across Sites from the same facts. It is separate editorial publishing, not an automatic daily change ranking, email spam, outreach harvesting or Harvest metric microservice. Sharing individual yearbook links with site owners remains manual/opt-in initially.

### Storage boundary
No annually repeated raw request snapshots. Store compact normalized before/after facts only on meaningful change, one small daily coverage summary per known tracked source/day and versioned annual snapshots. Establish actual per-site-year SQL/WAL/heap/index growth on sample data (e.g. 100, 1000 sites) and cap JSON payloads/number of events and output document size. Avoid storing full Steam News bodies or site HTML; no new MongoDB/Timescale/ClickHouse. Historical facts survive Harvest replay-window expiry and snapshot reset.
