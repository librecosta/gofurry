# GoFurry V0.1-D3-A2-A — Steam Metadata & Durable Source Projection

**状态：冻结 / 第一实施批次** · 2026-11-13
**仓库：** \`librecosta/gofurry\` · **分支：** \`develop\`
**依赖基线：** \`aff65e4923a0490543287599b57b792e5db71888\`（D2/D3-R1 修复与验收通过）
**D3-A2 的下一批：** D3-A2-B Steam Incremental Discovery & Automatic Eligibility。A2-A **不要**抢跑新的 Harvest catalog Provider、AI 分类器或游戏页面。

## 0. 第一原则

本阶段专门修复一件事：**Harvest 早已采集到 Steam 的完整合法资料，但 GoFurry 当前 Consumer \`normalizeSteam\` 丢弃很多字段**。让 GoFurry 正确消费这些字段，形成来源明确、持久可读的游戏资料；为下一批自动发现和自动分类提供高质量输入。

**不可再次出现的设计缺陷**：一个已发布 Game 在资料过期、Harvest 停机、Consumer 410/reset、换平台、来源停止响应、原 Observation 被清理、30/180/365 天不采集后，其 Public ID、标题、简介、SSR 可见性不可因时间条件或临时投影丢失而隐式改变。D2/D3-R1 为最高优先级。价格/当前玩家数有时效性，但基础作品资料和历史新闻不得靠 TTL 隐式下架。

不得新增“每次采集以后重新审核一遍”“每 180 天复审”“没有续期就下架”或双证据人工必填流程。A2-A **不新增任何必需的人工工作**，不更改已有首次发布的内容安全边界；自动候选内容分级在 A2-B 完成，不要声称 A2-A 已无人自动发布所有新游戏。

## 1. 代码和实际 Provider 契约

实施前必须查阅：
- \`AGENTS.md\`、\`.agents/architecture.md\`、\`docs/v0.1-d3-a1-acceptance.md\`、\`docs/v0.1-d2-d3-r1-acceptance.md\`、\`docs/v0.1-d3-a1-automated-game-intake-multi-source.md\`；
- \`services/api/internal/collection/{normalize,project,consumer,intake,intake_identity}.go\`；
- \`services/api/internal/catalog/{game,public}.go\`；\`services/api/internal/database/queries/{games,collection,intake}.sql\`；迁移 \`202611120004\` 和 \`202611130001\`；
- Harvest 已有 \`internal/provider/steam_details.go\` 与 \`steam.go\`（只读，不修改外仓）。

Harvest \`steam.details\` output schema v1 已分 \`details\`、\`price\`、\`media\` 三个 scope。真实采集字段（按现存实现核对，而不是猜测）：
- details: \`name\`、\`type\`、\`description\`（Steam short description 纯文本）、\`supported_languages\`、\`developers\`、\`publishers\`、\`platforms\`（win/mac/linux 保留 absent/false 区分）、\`categories\`、\`genres\`、\`release\`（coming_soon 和原始 date_text）；
- media: \`header\`、\`capsule\`、\`screenshots\`（现有 Provider 最多 8）、\`movies\`（最多 4）；
- price: \`state\`、币种、initial/final minor units、discount_percent，按每个商店地区 + locale 的具体 scope；
- news, players 为各自已存在能力，**不混入 \`details\` 作品主字段**。

当前 GoFurry \`normalizeSteam\` 的 details 只消费 Name/Type、media 仅 Header/Capsule；所以要扩展其 **typed, bounded, source-attributed normalization**，但必须保留已有 schema v1/聚合协议兼容，允许以前已保存的少字段数据安全读取。不得改动 Harvest 的输出 schema 或伪称某个字段已被采到。

## 2. 正规化规则（不任意覆盖）

- 由 \`game_sources.platform_code='steam'\` 与 AppID、正式 \`collection_bindings\`、真实 active generation + scope + schema + ruleset 校验后，才可以归属于某个 Game；绝不以名称匹配直接跨 Game 更新。
- 一次 \`steam.details\` 可以是语言 \`en/zh-cn\` × 店区 \`CN/US/HK\`；只在源范围内保存事实。展示名称/简介选择必须有稳定的 locale 优先级，店区变化不应该导致标题抖动。英文内容不自动冒充中文；中文来源真实存在才映射到 GoFurry \`zh\`。
- 清洗 \`description\` 与 \`supported_languages\` 等来自上游的文本：纯文本显示、去控制符、限制字节/字符和数组大小；禁止 raw HTML、\`v-html\`、不可信 Markdown/脚本执行，不自行翻译或编造内容。开发商、发行商、类型、平台支持只表达**来源所述**，不自动推断“全平台支持”。
- \`release\` 保留 \`coming_soon\` 三态（true/false/unknown）和原始 date_text；若做日期解析，必须显式保留精度与“不确定/未能解析”，不能把 \`Q3 2027\` 默认为 \`2027-07-01\` 或把 Steam 上架日期当成作品首次发行。
- \`categories/genres\` 的原始 Steam code + name 按 Provider 已排序去重，未来 D3-A2-B 才映射 GoFurry 受控 Game taxonomy；**A2-A 不建立永久固定的误分类映射**。
- \`price\` 仅按 Steam 来源/商店地区/货币/最后观察时间有效；优惠折扣/玩家人数绝不加到 Game 的全平台通用字段，不把未知值变成免费或 0。不因为一个地区的不可用覆盖另一区域。
- \`media\` 复用 Harvest 已验证的 Steam 资源域名及 URL 校验，并在 GoFurry 重新检查 HTTPS、来源白名单、长度、重复和媒体数量；不下载完整视频至 R2、不额外引入第三方代理、不对 SSR 时做远程媒体 HEAD。无效链接不提供点击或播放，不阻止其他资料持久展示。
- 新证据为相同值时仅记录确认时间或不作写入；新证据不同但有效时更新 **自动资料快照**，同时保留原有来源与时间。采集失败/confirmed_empty/withdrawn/Consumer gap 不清空已经发布的稳定资料；如事实明确撤回，仅将对应来源标记不可作为**当前**事实，保留已发布文档的历史来源并将展示和真实更新状态分离。

## 3. 最小持久投影

优先在 GoFurry regional PostgreSQL 中新增**少量来源维度的结构化持久快照**，例如一张有界 typed \`game_source_metadata\` 表（或论证现有结构即可充分承担）；唯一关键为 \`game_source_id + locale + store_country\`（根据 provider 的数据共享语义适度规范化，避免重复标题）。可分开少量字段或有限 JSONB，但 JSONB 必须 schema-versioned 且有真实字段校验/大小限制，禁止保存 Steam 原始 appdetails 响应、生成任意 EAV 或为每个 metadata 字段建一张表。

快照持有：真实字段、provenance 的 \`observation_id/content_hash/ruleset/observed_at/confirmed_at\`、source 标识、scope、最后成功自动选择的展示信息。对 \`price\`、\`news\`、\`players\` 尽量继续复用既有 \`collection_current\`、\`game_evidence_news\`、\`game_evidence_players\`，A2-A 不随意新建第二份事实历史表。

- \`game_approved_presentations\` 是 D2/D3-R1 的**已批准且持久**的自动公开名称/简介快照，它必须保持权威；如果来源元数据更新确有实质改进，按明确、幂等的更新规则刷新其中的自动值，**绝不改写 \`game_localizations\` 人工编辑值**。
- 对既有 D1 人工发布 Game、A1 intake-managed Game、多个 Steam source 的 Game，都要保证没有未批准的来源趁刷资料更改主展示来源/发布状态；已明确选择的来源稳态保持，不按“谁最后采集”切换。
- Consumer/数据库事务内先成功确认当前 Observation 的归属，再更新来源快照；必要时和已有 Cursor/ACK 事务协调，避免 ACK 已前进、快照丢失。snapshot/reset 恢复应重建现有来源投影而不破坏持久已发布资料。
- 已有 published Game 的快照属于业务发布资料，不受短期 Candidate \`review\`、\`next_at\`、\`active\`、Worker 停机和固定 TTL 限制。若数据从未存在，允许显示真正缺失字段，不伪造封面/语言/发行状态。

## 4. 完成后具备什么读取能力

新增内部 typed \`GameSourceSnapshot\` 与 \`GamePresentation\` 域读模型（可复用现有 catalog/public API 做有界兼容扩充，**不要新建广泛公开详情 UI**）：
- 统一游戏身份 + editor/auto precedence；
- 每个已绑定平台来源的元数据、观察范围、真实数据来源和有效的媒体 URL；
- 与价格、News、players 的来源/地区分别对应，但缺少动态观察时资料主体仍完整；
- 纯服务端解析/一次性批量查询，不在公共 Game SSR 期间发 Harvest/Steam 网络请求，不 N+1；
- CN/INTL 功能模型一致，地区 DB 分离；当前真实 Harvest consumer 只在 CN，INTL 继续既有可用资料读取，不为 A2-A 新建跨区域双活采集。

前端 /games 完整发现、截图画廊、价格趋势、玩家分析等属于 D3-B/C；A2-A 只需数据契约和少量必要兼容读模型，不添加空 UI 或装饰卡片。

## 5. 实施顺序

1. 更新 \`normalizeSteam\` 的 typed 保留字段，并补上 schema/locale/market/URL 与 bounds 测试。
2. 新 Goose forward migration（旧迁移不可编辑）及 sqlc typed query，保存最小持久来源快照。
3. 将消费、snapshot/reset 和已存在 Intake 的已批准自动资料刷新路径与新快照联通；不能破坏已知 Observation 归属与 Candidate 保护。
4. 暴露有界的服务内部 Game source read model；适配完整能力缺省值、既有 API 和 SSR。
5. 完成隔离端到端验收及真实 CI，生成文档并停下，不提前做 Steam 全站 discovery/AI/itch。

## 6. 验收

在隔离 PostgreSQL18.6 + Redis8 + **真正 Harvest Server/Worker**、模拟 Steam Storefront 上游运行以下案例：
- en/zh × CN/US/HK，各语言来源真实显示，跨市场不乱覆盖；Steam details 三个 Scope 都能被规范化，媒体截图<=8、视频<=4、开发商/发行商、语言、发行日期精度保留。
- 单平台和多平台 Game、Steam 两个 AppID 指向不同 Game、人工中文编辑、自动英文来源。任何刷新不能越界、不能抹除编辑、不能把 Steam 玩家当全平台玩家。
- valid new / unchanged / withdrawn / malformed/partial response，旧 schema 少字段，Consumer 410 reset、新旧 source binding、第二个网站无关 Target 的隔离；不泄漏原始 HTML、脚本、媒体危险 URL、私密来源。
- **跨时钟 31/181/365 天 + 停止 Harvest**：公开 Game 依然 200、标题/简介/资源选择及 Public ID 稳定；价格/当前玩家时效独立。测试不能只用快进后重新注入合法资料来伪造结果。
- 已接受但未获首次发布资格的 Intake 候选，不因 A2-A 获得更多 metadata 就偷偷变成公开 SFW；已有明确封禁不被新采集解除。No new manual review or timed expiry.
- 数据恢复/并发重放/重复 observation 幂等，旧 D1、Site、导航、年鉴、Start、壁纸全部正常；性能测试 100/1000/10000 source snapshots 的有界读写。
- 执行 \`task sql:check\`、\`task check:api\`、\`task check:catalog\`、\`task check:collection\`（pinned Harvest）、适用 Web/HMR/Docker/Containers；最终匹配 SHA 的 GitHub Actions success。

**交付**：\`docs/v0.1-d3-a2-a-acceptance.md\`，列出各字段为何落入哪个来源范围、迁移、更新/回退判定、持久资料示例、证据与实际测试、Commit SHA/CI。不得声称 A2-A 已实现 Steam 全站自动发现、兽人/NSFW 自动分类、itch Provider 或游戏首页。

## 7. 下一步：D3-A2-B（目前仅规划，A2-A 结束再冻结）

- Steam 官方 \`IStoreService/GetAppList\`，要求**任意 Web API Key**、支持 \`if_modified_since\`、\`last_appid\`、游戏过滤。旧 \`ISteamApps/GetAppList\` 已弃用；官方文档：https://partner.steamgames.com/doc/webapi/IStoreService。
- Harvest 应增加独立、受配额控制的**分页 catalog discovery capability**，支持 API Key 仅保存在私有 YAML、控制可见限流以及固定来源地址；不得让前端或 GoFurry API 绕过 Harvest 直接请求 Steam。
- Steam catalog 规模远大于当前 10,000 条待处理 Intake，必须使用可恢复增量游标、轻量去重/筛选与单独候选预算，而不是一次把所有 AppID 深度采集。索引仅说明应用存在/变更，不证明兽人相关性或 SFW。
- 使用 A2-A 的可信资料作为自动语义分类输入；在实际标注数据上验证兽人相关性/成人内容误判。允许自动分类以降低人工，但**不得强迫每款游戏提交两份人工证明，也不得按时间到期重审已发布内容**。任何导致下架的成人内容决策必须是持久、显式且可追溯的具体判定，而非“模型不可用=隐藏作品”。
- Harvest “同值确认无法关联 Job/Attempt”的契约缺口需要单独最小补丁并隔离验证。优先继承已存在稳定资料和 Job 可证明的状态，不盲目重发，不能当作拒绝所有自动处理的常态。
- A2-B 完成后才进入 D3-A3 itch 可行性、D3-B/C 页面。

**本阶段不改 Harvest/steam-go/旧站仓库**，不提交密钥、不部署生产、不改共享开发 DB、不覆盖人工资料、不引入新人工负担。
