## 0. Fundamental product policy

GoFurry is a **long-lived, low-human-operation catalog**, not a volatile cache of Harvest results. Its public Site/Game business identity and approved, published, stable presentation facts **must not silently vanish** because:
- 30/180/365 days passed, or a periodic confirmation/review was not repeated;
- Harvest/Steam/HTTP/CDN/Redis is unavailable, blocked, throttled, or late;
- a Consumer reset, 410 gap or replacement of active generation occurred;
- Heat is cold/stale, there were no views, a category is missing, or a provider lacks a field;
- a GameSource or Site collection binding temporarily becomes unavailable.

\`published\` remains durable until **explicit, persistent** archive/unpublish or a concrete, recorded adult-content policy intervention. No implicit TTL, cron transition to draft/archive, automatic deletion, dynamic SQL condition invalidating an already-published entry, hidden mandatory re-review, or silent field wipe. Identity and stable facts persist; **only truly current observations** (price, live player count, last observed HTTP/TLS or current Heat) have freshness semantics. Old values can be marked \`last_observed\` with actual timestamps and must never be called \`current\` after they become outdated.

**Automation over bureaucracy**: ordinary Site/Game classification and enrichment should be automated whenever reliable source material and rules exist. Review/CLI is an *exceptional correction* capability, **not** a default per-item human gate, and there is no periodic human renewal. This contract does not magically authorize unknown/adult material as SFW: distinguish automatic classification supported by evidence, unknown classification requiring more information, and actual adult content policy intervention. Never fake safety findings.

## 1. Code findings to correct (actual current code)

### Game — high severity
- \`services/api/migrations/202611120004_game_intake.sql\` defines \`game_presentation()\` with \`review_until > statement_timestamp()\` and \`profile_at > statement_timestamp() - interval '30 days'\`.
- \`services/api/internal/database/queries/games.sql\` conditions \`PublishedGame\`, \`PublishedGamePage\` and \`CanPublishGame\` on dynamic \`game_presentation(...)->>'approved'\`; the published Game can silently 404/leave catalog when time passes or the Candidate becomes unavailable.
- \`game_localizations\` is editor-owned; automatic presentation currently relies on transient candidate/source state, so a stable published snapshot needs to be persisted **separately** without rewriting human text.

### Site — different problems, not the same 180-day expiry
- \`services/api/migrations/202611120001_navigation.sql\` defines \`site_public_navigation\` as \`status='published' AND content_rating='sfw' AND primary_category IS NOT NULL\`. \`CanPublishSite\` also requires a primary category; newly created Sites default to \`unreviewed\`. **Primary category is discovery metadata, not an existential publication requirement**.
- Previously published D1 Sites were marked \`legacy_detail=true\`: historical detail/yearbook preserved, but discovery/catalog hidden until a distinct \`navigation review\`. This causes an expensive mandatory secondary editorial step and needs a forward-compatible, provenance-aware route to normal public discovery without inventing facts.
- \`services/api/internal/database/queries/site_profile.sql\` requires current generation AND \`confirmed_at\` within 30 days for technology facts. Thus technical *context* disappears after 30 days/Consumer gap, though the Site itself stays published. Preserve the last attributable verified observation as history while avoiding false \`current\` claims.
- **Site has no discovered 180-day content-rating expiration** and Harvest outage does **not** by itself archive Site. The fix must not claim otherwise.

### Not defects: preserve correctly scoped freshness
- \`navigation.heat\` uses 7 UTC days and stale after >2h; its qualified trending/ranking can honestly be empty/fallback, without changing Site visibility.
- Yearbooks have an explicit \`hidden\` status. Once published, an existing year's revision should not vanish simply because a later year lacks sufficient coverage; unpublished years aren't expected to appear.
- Fixed editorial featured slots don't expire on a timer. Explicit archive or prohibited adult content can remove a Site from *effective* featured display, not delete the assignment.

## 2. Game durability repair — include all Game-only R1 requirements

1. **New forward-only Goose migration** (do not edit \`202611120004_game_intake.sql\`) removes all 180-day human-review and 30-day profile freshness gates from Game publication and public reads. Retain \`reviewed_at/profile_at\` as provenance only, never as a published eligibility TTL. An existing approved/published Game stays public until explicit archive or recorded adult-content policy intervention.
2. At initial automatic publication, **persist a minimal stable approved presentation**: one actual name+summary+language and chosen source/provenance. Respect existing editor-owned \`game_localizations\`; auto updates may replace the *automatic* snapshot on verified material changes, not human text. Preserve last successful snapshot through provider failure, source removal, Candidate reset, 410, or new source selection. No generic EAV or full CMS.
3. Public Game detail/list/SSR must read \`published\` and persistent presentation; dynamic current Candidate or current Harvest status must not govern public entity existence. Restore previous published rows without requiring their past 180-day operator references to be renewed. Never replace missing historic facts with fabricated text. Prepare explicit diagnostic if legacy published record has insufficient reconstructable content.
4. Current price, discount, Steam players and similar *real-time* fields retain source/market/\`observed_at\` and own freshness policy. They may be labeled historical or omitted as current but cannot unpublish the Game.
5. No scheduled human renewal. First-time content policies are considered during initial publication; unknown/adult content isn't implicitly made SFW. **Do not introduce a new two-proof mandatory per-Game operator workflow.** Genuine automation of first-time positive classification belongs to D3-A2; this correction must not pretend a classifier already exists.
6. Explicit adult policy revocation must be stored as a durable, attributable decision with a clear reversal path, not a SQL time check. Existing editor-published D1 Game and Public IDs remain intact.

## 3. Site — remove artificial manual/category publication gate

1. Amend \`site_public_navigation\`, \`CanPublishSite\`, list/home/search/related/read projections so **missing \`primary_category\` cannot remove an otherwise legitimately published, content-policy-eligible Site** from complete directory, search and detail. Eight category filters remain fixed. A Site without a classification belongs in the unfiltered directory and text search, but not any arbitrary category count/filter; the UI shows \`未分类 / Uncategorized\`, never guesses one.
2. Update D2-B \`Card\` decoding and list/detail components to support an optional primary category safely; no \`categories[undefined]\` crash, broken SSR, or hidden entire card. Only category counts use real categories. Related may rely on shared tags when categories are absent; fewer/no recommendations are fine and do not determine owner visibility. Reassess editorial featured slot's category dependency separately: never silently erase slot assignment due to missing category.
3. **No mandatory second \`navigation review\` step for every new normal Site.** Classification may be computed from reliable sources on intake/normal catalog edit, and unknown classification stays optional; D4 Admin should only intervene for exceptions. Keep the explicit review command as exceptional correction/audit, not as recurring work. A confirmed adult/mixed classification may prevent public display under current SFW policy.
4. For existing D1 \`legacy_detail\` publications, build a **bounded, re-runnable, non-destructive upgrade/diagnosis**. When previous trustworthy publication/SFW evidence can be proven from legacy policy or upcoming D5 import evidence, inherit it once without mandatory per-row manual re-review. Where actual adult policy is unknown, **do not fabricate SFW**, and preserve the existing compatible minimal detail/yearbook paths and report the reason until automatic evidence becomes available. No mass automatic archive or data deletion.
5. Content rating is a **durable decision**, not a lease. Changing text/address/logo or missing periodic Harvest facts does not clear it. Explicit recorded adult-content policy intervention may hide a Site and must have persisted reason, date, provenance and reversal semantics. Don't make CN impose any extra business/content restriction except adult material and comments; INTL currently uses its existing SFW public policy pending future feature decisions.
6. Don't build a generalized compliance workflow or force a new "approve" click for every Site. Show honest unknown metadata and focus human operations on exceptional conflicts.

## 4. Site — verified historical technical context, not a time bomb

1. Stop treating \`confirmed_at >= NOW()-30 days\` as an **automatic deletion from the historical informational display**. Preserve and surface up to five trustworthy, attributable *last known* facts from an existing compact evidence ledger or a minimal durable summary. These may be old; show actual \`last_observed_at\` and status \`last_observed\`, never “currently healthy” or “currently uses X” for outdated evidence.
2. A recent verified current-generation fact may be described as recent observation; the last snapshot through 31/181/365 days, temporary Harvest outage or Consumer reset may fall back to history with time and source. The fact's retention needn't be a universal new 365-day TTL. No every-request Harvest, HTTP probe, raw source JSON, time-series dashboard or new service.
3. **Attribution matters**: a previous Site's domain, a closed/rebound binding, another Site's shared Target, removed or invalid scoped fact, withdrawn evidence and unknown ruleset cannot be presented as current evidence for a different website. Older domain history should be marked historical and only when trustworthy.
4. An expired TLS certificate or a once-200 HTTP status must never claim present-day validity, availability, safety or uptime; historical data may show what was last observed.
5. Existing public yearbook's archived evidence and URL behavior stay stable; do not replace it with a new history product.

## 5. Preserve legitimate operational freshness

- Heat 2-hour staleness, seven-day counts and cold/low-sample ranking are short-window measurements, **not entity availability**; keep honest fallback and never remove sites from catalog.
- A new year's yearbook can be absent due to insufficient evidence; an older published yearbook must not disappear because Harvest is off, another year starts or no additional coverage arrives. Existing explicit hide functionality stays explicit.
- Featured editorial assignments persist, and no periodic expiry is added. Missing current data only adjusts dynamic decoration.
- Missing R2 asset/CDN or Redis must use a harmless image fallback/stat omission without clearing stored reference or Site/Game.
- A true PostgreSQL outage results in 503, not a false 404 or a fake empty response.

## 6. Implementation guardrails

- One scoped GoFurry repo change, one or more **new** Goose forward migrations. Never edit already applied historical migrations, don't touch Harvest repo, Steam SDK, old site, Start appearance, Site navigation layouts (except necessary optional-category/historical label), Yearbook archival rules or D3-B/C.
- Explicit config files only. Go 1.27.3, Fiber v3, PG18, sqlc+pgx, UUIDv7, encoding/json/v2. No new auto-increment, arbitrary FK cascade, EAV, separate backend service, generic CMS, manual-review queue, AI billable call or speculative policy engine.
- Site/Game stable snapshots/editor data must survive repeated migrations, concurrency, source change, processing abort and replay. No implicit state mutation from GET or scheduled refresh; all substantive publication/policy changes require an explicit persisted decision.
- Never run destructive tests or schema migration on shared development or production. Use disposable PG18/Redis/Harvest fixtures and retain prior Source IDs, Public IDs, Slugs, approved Site assets and yearbook revisions.
