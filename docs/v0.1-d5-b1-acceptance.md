## 在隔离环境执行

1. 在一次性 PostgreSQL 18 实例中准备 CN development 数据库，名称使用 `gofurry_d5b1_` 前缀。由测试库所有者为这次环境生成独立 UUID，并设置数据库备注 `gofurry-d5-b1:<UUID>`。普通应用使用自己的 YAML。导入器会同时检查数据库名、备注、PG 主版本、UTF8 和 Goose 版本 `202611150003`。
2. 用只连接该实例的私有 GoFurry YAML 显式执行 `task migrate ACTION=up CONFIG=<绝对路径>`。使用独立的导入 YAML 和已验证的离线 Seed。计划和报告放在访问受限、Git 忽略的目录中。Windows 由目录 ACL 保护文件。
3. 使用相同配置执行以下三条命令。`plan` 是只读预检，输出计划 SHA256。审核精确的计划文件后独立确认 SHA256，再传给 `apply` 和 `verify`。各操作使用新的报告文件名。

```text
go -C services/api run ./cmd/legacy-import plan --config <import.yaml> --plan <plan.json> --report <preflight.json>
go -C services/api run ./cmd/legacy-import apply --config <import.yaml> --plan <plan.json> --plan-sha256 <approved SHA256> --report <apply.json>
go -C services/api run ./cmd/legacy-import verify --config <import.yaml> --plan <plan.json> --plan-sha256 <approved SHA256> --report <verify.json>
```

配置路径使用绝对路径。以下示例的数据库记录、凭据、哈希和目录均需用测试环境自己的值替换。没有核准 Logo 时可省略 `storage`。对象接口和公开测试 CDN 都须使用字面量环回 HTTPS。为局部测试 CA 提供 PEM 文件。

```yaml
seed_dir: /private/d5/sealed/snapshot-example
snapshot_id: snapshot-example
backup_sha256: "<independently verified backup SHA256>"
content_sha256: "<independently verified manifest content SHA256>"
legacy_deployment: gofurry_nav_site_cn
region: CN
environment: development
isolation_token: "<UUID from the database comment>"
decisions_file: /private/d5/decisions.json
database:
  host: 127.0.0.1
  port: 5432
  name: gofurry_d5b1_example
  user: "<isolation database role>"
  password: "<isolation database password>"
storage:
  endpoint: https://127.0.0.1:18443
  public_base_url: https://127.0.0.1:18443/cdn
  region: auto
  bucket: gofurry-d5b1-example
  access_key_id: "<test-only access key>"
  secret_access_key: "<test-only secret>"
  ca_file: /private/d5/local-test-ca.pem
```

`decisions_file` 采用严格 JSON，顶层包含 `decision_schema_version: 1`、`content_sha256` 和 `decisions`。每条决议提供 `operation`、`subject`（`{"table":"gfn_site","key":[1]}`）或列出具体源键的 `subjects`、`reviewer`、`reason`、`evidence` 和 `value`。复合关系使用完整键。由有权执行 D4 Owner 决策的人核准分级、发布和既有身份决议。回执保存哈希，相关证据由运营在私有决议文件中归档。

| 决议 | `value` |
| --- | --- |
| `supply_slug` / `resolve_tag_code` | 字符串，分别为规范 slug 和游戏人工标签或类别代码 |
| `map_group` | 旧分组填写 `{"category":"community","tags":["forum"]}`。单站覆盖可填 `primary / secondary / tags` |
| `select_address` | `primary` 和 `alternates`，值分别为源候选键与候选键数组 |
| `select_source` | 列出已有源证据的 `platform_code / external_key / source_url` 对象，`source_url` 可省略。空数组表示核准舍弃所有当前来源候选 |
| `link_existing` / `alias_existing` | `target_id / kind / public_id / revision`，标签及类别的 Public ID 为空。别名仅限 Site 和 Game |
| `resolve_relation` | `{"ignore":true}`、人工标签关系的 `{"role":"primary"}` 或人工合集成员的 `{"position":1}`。显式排序时提供保留下来的完整顺序 |
| `allow_logo` | D5-A Logo 索引核准的 64 位 SHA256 |
| `allow_publish` | Site/Game 用 `{"sfw":true}`，合集用 `{"relations_approved":true}` |

保持 Seed 内容、决议、计划及目标不变即可安全重试。已提交的写入按回执和当前编辑前像核验。事务失败只回滚本单元，已验证对象可复用。遇到人工修改、来源争用或待决字段，保留现状并在报告中定位。解决问题后生成新的审核计划，重新核对原映射。已经提交的编辑变更由带 revision 的常规补偿处理。私有报告列出每个源键的唯一对账状态、阶段结果、目标 UUID 与 revision、合集计数和素材结果。控制台只输出状态、哈希和汇总行数。`apply` 和 `verify` 在未结案时返回非零。

## Schema 和验收

- `202611150003_legacy_editorial_import.sql` 增加 D1 Site/Game 身份映射、有限类型的人工编辑映射、导入批次和阶段回执。D1 映射使用两条限制删除外键。游戏人工标签和类别有独立关联和归档状态，合集有标签规则、显式排除和共用的有效成员查询。Catalog 继续用既有公开资格和手工编辑规则。
- 使用 D5-A SQL 与真实格式图片生成的合成 Seed 在一次性 PostgreSQL 18 和本机 TLS S3/CDN 替身中验收。主夹具对账 57 条，尝试两次失败的单元后恢复，完全重放复核 36 条，两个 Logo 绑定共用一次条件 PUT。两个快照复用身份，编辑者清掉 Logo 后重放保留其决定。511 和 512 项合集完整提交，513 项合集的人工成员、规则与排除一起暂缓。
- 隔离验收覆盖同数字不同实体、已有 Steam 来源和采用时的人工数据保护、批准的 itch.io 作品链接、原子写入、成人及 Unknown 隔离、历史地址留证、人工/自动/排除成员、归档暂停规则、公开合集游标失效、Seed 损坏、目标标记和区域校验、对象上传后绑定失败、公开交付失败与批次锁。
- 本地通过 `task check:api`、`task sql:check`、`task check:legacy-seed`、`task check:legacy-import` 和 `task check:catalog`。Catalog 原有 CN/INTL 浏览器用例通过。游戏目录在路由载入新筛选条件时隐藏旧分页链接，以保持游标和筛选条件一致。GitHub Actions 在 `legacy-seed` 作业中同时运行冻结的 D5-A 和 D5-B1 验收。

## D5-B2 的输入

真实备份及生产内容未提供。进入真实数据验收需要 D5-A 的私有恢复与已核对哈希的 Seed，以及来自真实数据的 Steam/itch 归属冲突、Site 地址、分组映射、正面 SFW 证据、异常关系和 Logo 覆盖清单。通过隔离目标的只读计划确认实际冲突数量、合集规模和对象交付，再逐项决定处置。没有可靠依据的内容继续作为草稿或报告中的待决项。数字旧 URL 仍由后续迁移策略决定。
