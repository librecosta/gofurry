# GoFurry V0.1-D3-A1 — Automated Game Intake & Multi-Source Identity Contract

**状态：冻结 / 实施契约** · **2026-11-12**  
**仓库**：`librecosta/gofurry` · **目标分支**：`develop` · **基线**：`67deca9c2bd3d011d9142d9b75215214f75e68cd`  
**产品核心原则**：Game 身份独立；发行来源独立；采集事实归属于具体来源；高度自动化；只把真正有价值的异常交给人工。

阅读顺序：`AGENTS.md`、`.agents/architecture.md`、`docs/v0.1-d1-a-site-game-identity-url.md`、`docs/v0.1-d1-b1-acceptance.md`、`docs/v0.1-d2-c-acceptance.md`；核对现有 `catalog/game.go`、`catalog/identity.go`、`collection/{bindings,consumer,normalize,reconcile}.go`、`queries/{games,collection}.sql`、`Harvest` 的真实 Targets / Jobs / observations/history / Consumer HTTP 契约。

## 0. 本阶段目标及非目标

**D3-A1 一次性完成可运行的低人工建档基础**：从一个规范化的可信平台候选开始，完成重复识别、受限预采集、来源匹配、自动创建 Game 与附加 GameSource、基本资料自动投影、SFW 与兽人相关性判定、条件自动发布、继续采集的绑定与调度意图、后续观察的幂等更新及异常状态。提供可控且有界的运行入口和隔离验收，避免再次只写“未来会自动化”的空契约。

**D3-A1 不负责**：Steam 全平台 GetAppList 增量扫描与发现器（D3-A2）、真实 itch.io Provider（先 D3-A3 单独验证）、完整 Steam 多字段/截图/媒体消费与搜索标签（D3-A2）、Game 首页/目录/合集/详情（D3-B/C）、可视化 Admin（D4）、真实旧数据迁移（D5）、地域投影（D6）、生产上线。评论和抽奖**完全不在 D3 范围**，不得预建空表、路由和“稍后开放”假入口。不得顺手修改 Start、Sites、Site Yearbook、壁纸、外部仓库和全局视觉。

本阶段具备真正可测试的 **“向自动 Intake 提供一个有效 Steam AppID → Harvest 完成一次性预采集 → 自动决定身份并在满足条件时建档/发布 → 形成持续订阅”** 路线。批量发现候选的“种子来源”与 Steam 增量发现留 D3-A2，但 A1 不能仅用静态假对象模拟上述真实 GoFurry↔Harvest 业务路径。

## 1. 三个独立身份及一条硬边界

- **Game**：作品的独立 UUIDv7、随机 16 位 Public ID 和规范 Slug；身份与 Steam AppID、itch 页面、域名、采集 Target 都无关。一个作品可以存在多个发行渠道。
- **GameSource**：`game_sources` 中平台发行条目，平台代码、规范化唯一外部标识、官方条目 URL、active 状态。每个平台外部标识只归属一个当前 Game；Steam AppID 需要保留现有严格的 UINT32 校验。任何已存在来源不能被并发流程重新绑定到另一个 Game。
- **Harvest Target / Observation**：采集系统自己的目标、能力、观测范围、时间、规则版本、原始数据。它不是 Game，也不是 GameSource；一个 GameSource 可能有多种能力/范围及多个受审核的数据提供者，不假设永远一个平台=一个 Provider。
- 已有 `collection_bindings` 记录正式归属。**候选预采集时 Game 可能尚不存在**，不能直接要求已有 GameSource 才能完成资料预采集，也不能偷偷让未绑定事实流入正式公开投影。

**首轮支持**：生产仅 `steam` 可采集；其他平台可以安全地登记官方来源链接但不冒充支持了自动采集。第二平台的匹配测试使用明确标记的模拟 Provider，不引入虚构的生产 `itch.details` Capability、外网抓取或第三方登录令牌。

## 2. Candidate 生命周期与去重

最小状态集（作用于候选，不与 `games.status` 混淆）：

- `discovered`：收到新的、有效且规范化的来源标识；
- `resolving`：单个执行者取得有限租约，等待/读取可信资料并判断已有关系；
- `accepted`：已归属到一个 GameSource 和 Game，后续交给正式采集；
- `deferred`：证据暂时不足、请求失败或身份有歧义；有明确 reason_code、可重试时刻或新证据触发条件；
- `rejected`：已知并非本目录作品、仅附属商品、来源被确认无效等，保留短小拒绝原因与可重新评估条件，不周期性无限重试。

自动发布属于 **Game 自身 `draft|published|archived` 生命周期**，不新增 Candidate 的 `published` 状态；accepted 但未批准 SFW 的 Game 可以继续是 draft。

要求：
- 候选稳定去重键 `(platform_code, normalized_external_key)`；同一键不同大小写或发现方式反复进入必须合并到同一候选。二级索引和唯一约束以数据库保证，并发提交不可重复建档。
- 只存必要字段：平台身份、来源、状态/原因、被接受的 GameSource/Game 引用、候选资料小摘要、已处理证据摘要和版本、下一次适用处理时间、必要 CAS/revision 与时间戳。不要建海量每次观察审计事件、原始 JSON 仓库、泛型工单数据库；历史详细日志留 Harvest。
- 调度/重试有上限、退避、持久化去重、租约过期恢复。后台不会因为同一候选重复失败而累积多个待办。Rejected 的重复发现不能触发无限深度采集；Deferred 在无新证据、未到适用时间前不重复耗费配额。
- 所有关系修改和最后状态切换应在 GoFurry PostgreSQL 单区域事务内进行，防止 Game 创建成功而 Candidate/Source 丢失。外部 Harvest HTTP 操作绝不参与同一 DB 事务，必须持久化 intent 并重试/核对。

## 3. 未绑定 Candidate 的真实 Harvest 预采集通道

目前 `collection.Consumer` 仅把已有有效业务 binding 的 Observation 归属到 Game。D3-A1 **不得让它无条件摄取所有 Harvest 历史**，否则未审核目标跨数据域泄漏。

复用 Harvest 已有能力：`POST /api/v1/targets`（幂等来源注册）、`POST /api/v1/jobs`（支持 Idempotency-Key）、`GET /api/v1/jobs/:id` 及带 target 过滤的 `GET /api/v1/observations/history`（按 namespace/target/capability/有界时间读取）：

1. 内部 Intake 接受经过规范化的 Steam AppID，持久化唯一 Candidate 和预采集意图。通过只在已配置可信服务器上使用的 writer principal 注册 Steam Target，记录并核验 Target 的 namespace/provider/type/key。
2. 使用有界的一次性 `steam.details` Job，而不是为所有候选提前建立永久周期 Schedule。持久化提交 idempotency key/Job ID；遇到 HTTP 超时/不确定返回，先查询和核对远端 Job，而非换 key 盲目重发。
3. 用**已有允许的 reader/最小权限**读取该 Target 与 Capability 的已完成 Observation，验证 Job/Target/时间/能力/输出 schema/scope/ruleset/观察 ID 与内容完整性。只将所需且经过规范化的少量候选元数据返回 Intake，不能把 Harvest 原始 JSON 直接写入 Game 描述或 HTML。
4. 若当前 Harvest History API 不足以强验证“这份 Observation 属于本次 Job”，先在 D3-A1 中通过现有 Job 与 Observation 不变身份、时间及 scope 证明，或提出**极小的权威 API 契约补强**并单列阻塞验收；不可伪造确定性。禁止为了这个场景重构整个 Consumer 或把 Harvest 数据库连接进 GoFurry。
5. 只有决议 `accepted` 之后才建立现有正式 GameSource→CollectionBinding，记录持续采集计划意图并使用既有 Reconcile/Consumer 路线；Target 可以复用，不能在两个路径重复创建同一常驻采集计划。
6. 无 Harvest 配置/认证失效/上游超时/Worker 停机 => Candidate 保留 deferred，已公开 Game 继续可用。不得通过直接从 GoFurry 服务请求 Steam 官方 API 绕过 Harvest 限流和安全策略。

首轮入口可由最小、明确受控的 **本地 CLI** 提供 `game-intake submit steam <appid>` / `status` / `tick` / `inspect` 等；命令调用同一业务服务，不需要人工逐字段输入，也不对公众开放编辑 API。D4 Admin 直接复用该域服务。必要时使用现有 API 生命周期运行有界定时 Tick，默认关闭且通过单一显式 YAML 开关控制，不在每个 API 实例重复无限请求。不要创建第二套服务进程或额外任务队列产品。

## 4. 身份判断与自动跨平台关联

按**确定性、可追溯**顺序：

1. **已存在同一个 `(platform, key)`**：必须重用既有 GameSource 和所属 Game，幂等更新数据；其他来源、Slug、Public ID 不改变。
2. **可验证作品专属跨平台关联**：仅当来源页面或官方作品资料给出指向具体商品的明确链接，关系具备可信来源，并经过至少一个独立高强度交叉证据校验（例如双方作品专属链接、可核对的官方作品身份和类型一致），且只命中**唯一**已有 Game 时，允许将一个新来源自动附加到那个 Game。仅项目相同开发商主页、社群主页、通用商店网址等不能成为合并证据；模拟来源也必须证明这条规则。
3. **没有可确认关联、没有有意义歧义且符合 Game 类型**：自动创建 Game（先 draft），生成 UUIDv7/Public ID 和稳定 slug，关联来源。
4. **相似但证据不够/多处相互矛盾**：candidate deferred，保留最小可复核证据，不自动合并，也不要求管理员当场处理。
5. **已有两个公开 Game 才发现同一作品关系**：只产生高价值合并建议。第一版不能自动删 Game、移动公开 Public ID 或用单纯名称匹配做 301。后续 D4 的人工合并必须保留原始链接、历史引用与回滚规则。

名称、封面、开发者名称相同只是候选线索，不足以认定两个作品一样。不得仅靠模糊匹配分数阈值进行自动合并。Demo、DLC、Soundtrack、Bundle、工具和不确定应用类型不能默认创建“正式游戏”：优先识别商品/作品关系；D3-A1 可明确 deferred/rejected，不须完成全类型家谱模型。独立重制/续作通常不同 Game，不能把它们当作同平台版本。

每个自动关联留下最小可查依据：source identities、evidence kind、source/provenance、规则版本、时间和明确的归属结果。不得凭自我引用或单个不受信任字符串自动合并；错误关联必须能够受控撤销，历史 Harvest 数据不可因撤销归属而重写。

## 5. 自动公开：资格明确，但不增加无根据的人工门槛

Game 自动内部建档与自动公开为两个独立决策。

允许自动发布的最小必要条件：
- 有效且唯一的主作品身份、明确不是 Demo/DLC 等附属商品；
- 有可信 Steam GameSource（或将来合法的另一平台来源），可生成至少一种真实语言的名称、合理摘要、合法官方访问 URL，且可稳定生成 D1 URL/SSR；
- **正面证据支持**该作品属于 GoFurry 的兽人/拟人题材。不能仅从“有动物字眼”或标题相似证明；
- **正面可审计证据支持当前 SFW 内容等级**。缺失成人标签、HTTP 200、没有识别到 NSFW 关键词，均不能单独证明 SFW。规则不能判断时保持 `unreviewed`、继续自动补证据；不要求默认每个候选人工审核；
- 没有相同平台身份或同作品高置信冲突；权限、来源时间、来源完整性与地区发布状态可被核对；
- 自动发布决策记录版本、依据摘要和发生时间。撤销资格后按现有公开读边界立即隐藏或降级，不触发删除身份。

首版可以用固定、可测试的 SFW/兽人正向条件规则及**已有明确审核的可信种子/迁移资料**作为真实正面证据。不能声称 Steam 的商店字段就能验证任何游戏为 SFW 或兽人作品。不得为了达成自动发布测试而将所有无成人标签的游戏视为合规。未来可讨论 AI Gateway 辅助分类，但 D3-A1 不强制引入模型调用、AI 费用或不透明的自动发布判断。

**地域产品政策**：CN 仅限制成人内容与评论；INTL 当前公开实现仍仅 SFW，后续 Adult 由明确产品策略开启。其余游戏功能、平台、来源、价格地区、运营策略不人为设置 CN 特殊限制。当前 Harvest→GoFurry 仅 CN 内部消费由既有 D1-B 契约决定，INTL 的已审核内容投影留 D6，不因为本阶段而引入第二个在线 Harvest 消费者或跨地域数据库共享。

## 6. 编辑值、自动投影与数据所有权

牢记三个不能混写的数据源：

- `games`：作品身份、审核/发布状态与少量明确运营偏好；
- `game_sources` + `collection_current`：平台身份及具体 provider/capability/locale/store_country/time 的已验证事实；Steam 价格、News、玩家数始终只归属于 Steam App，不等于作品全平台值；
- `game_localizations`：既有人为编辑的 zh/en 内容必须保持独立权限与所有权，不可拿采集结果无条件 UPDATE/覆盖。

建议采用**最小自动展示投影**（可为小的按 Game+locale 聚合读模型或经评测充分的现有 current 查询），包括自动选择的来源与摘要，而非把每种字段拆成一张 provenance EAV 表。公开读取优先级：

`明确人工覆盖 > 已选且仍有效的自动来源 > 其他可信候选`。

- 不因“另一来源这次刷新比较晚”就切换标题、封面、简介来源；只有当前选定值失效、确实缺失或经审核的质量规则触发才重选。人工编辑一经明确设置不得被下一次采集覆盖。
- 源字段按 `(GameSource, capability, locale, market, observation)` 有明确归属。一个英文源不能冒充中文翻译；不用游戏所属国/TLD 推断发行地区。
- 当前 GoFurry `normalizeSteam` 只保留 Steam details 的 Name/Type 与媒体中的 Header/Capsule，而 Harvest 已有 Description、Developers、Publishers、Platforms、Release、Genres、Screenshots、Movies。**D3-A1 仅补自动建档与最小摘要必要字段**；全面无损投影及来源字段映射留 D3-A2，避免重复变更同一投影。
- Steam 玩家人数不可跟其他平台相加；Steam CN/US/HK 商店报价不可作为统一 Game 售价。上游失败时保留未过期、仍具来源语义的旧事实，过期自动降级隐藏，不用 `0` 或空字符串覆盖有效数据。
- 修改 `CanPublishGame` 等业务规则使自动生成且已通过发布策略的内容可以发布，不能再要求每个游戏都人工填一条 `game_localizations`。同时保留已有 D1 纯编辑 Game 的合法路径与 SSR 行为，不能删除或变造现有人工记录。
- 公开 Game 一旦生成 Public ID，即使后来补平台、换主展示来源、改变封面，也不重生 Public ID；slug 修改仍遵循 D1 301。

## 7. 最小数据库与工程约束

优先复用 `games` / `game_localizations` / `game_sources` / `collection_sources` / `collection_bindings` / `collection_plans` / `collection_current`。

允许且仅在论证确实需要时新增：
1. `game_intake_candidates`：来源键、生命周期、租约/退避、轻量决议、版本与必要指针；
2. 小型自动展示投影/来源选择元数据（若现有表不足）；
3. 少量必要的 Game 分级、正向兽人相关性和自动发布依据字段/约束；
4. 强关联证据可以保存在候选决议或极简记录中，**不要默认新增庞大的关系图/事件表**。

遵守：Go 1.27.3 / Fiber v3 / Cobra+Viper 单 YAML / PostgreSQL 18 / sqlc+pgx / UUIDv7。**新表默认无 FK、无级联、无自增 ID**；必须存在真实一致性收益时再逐项讨论 FK，不触碰 D1-A 已审定保留的四个高价值 FK。新表要有明确 PK/unique/CHECK/必要索引和数据清理规则，不留无界候选原始 payload、采集详情历史和日志。

只添加 Goose 前向迁移，不改写 D1/D2 历史。所有操作以 GoFurry 地区库作为身份最终判定权威，不在 Harvest 建立另一份 Game Business Catalog；Harvest 使用自身的 namespace 认证、egress policy、配额和 worker 限流。异步网络过程不能跨库事务；一次提交不确定结果必须 reconciliation、不能盲目重发造成两份绑定。

## 8. 低人工、低配额运营约束

- D3-A1 的初始“候选供给”应是明确、可验证的 Steam AppID 输入或现有受控导入数据；**没有全 Steam 发现时不要宣传已实现全平台自动发现**。D3-A2 的 Steam 增量发现将调用此同一 Intake 服务，不再开发第二套创建逻辑。
- 先处理较少可信、高相关候选，逐步增加吞吐，而不是用全 Steam App 索引挨个请求 Store details。每个 Intake 处理器有批量上限、重试退避、并发限制和上游预算；限流由 Harvest 控制，业务运营策略不能绕过 Harvest 官方预算。
- 运营状态基于少量清晰 reason code 聚合：自动完成数量、accepted 但 draft 的数量、证据待完善数量、持续异常数量、真正需要人工处理的关联冲突数；不开发复杂 BI、画像或通用待办系统。
- 人工动作应为“确认某条关联、修正资料或内容分级、驳回来源”等单个例外，不是每个作品多字段表单。自动分类的判断规则透明且版本化，错误能回滚；源事实重新采集不改变人工覆盖。

## 9. 验收场景（真实 GoFurry + 真实 Harvest 代码，外网用安全模拟）

验收使用**一次性 PostgreSQL18 + Redis + 实际 Harvest Server/Worker + GoFurry API**，真实 HTTP 授权和模拟 Steam 官方响应，绝不清空共享 Tailscale 开发数据库，不调用实际 Steam/itch 外网，保留已有 D2 全部回归。

1. 相同 AppID 通过手动提交、重复接收、并发 16 次和模拟未来发现输入，只产生一个 Candidate、一个 GameSource、一个 Game、一个确定 Public ID；候选重复处理不会重新发布/写假新闻。
2. 第一次未经绑定的真实 Harvest Target→one-shot Job→有界 Observation 查找→受控解析→自动 create/update→后续正式 binding/schedule；实际检查 Job 幂等/丢失 HTTP 响应与查询核对，证明没为每个候选预设永久 Schedule。只有正式绑定后的 Change Consumer 才成为常驻投影，未审核候选不能被公开 SSR 检索。
3. 对符合 **正面兽人相关性与正面 SFW 证据** 的模拟 Steam game，验证无人工逐项输入即可自动创建并公开。缺证据、非游戏 App、Demo/DLC、成人/未知内容、无法确定类型时只能 draft/deferred/rejected；不把缺 NSFW 标签等同确认 SFW。
4. 已存在 GameSource 不可被不同 Game 抢占；跨平台互证有唯一匹配时可自动 attach，同标题/开发者类似但无强证据时 deferred，双已发布 Game 只提案不自动 merge，解除关联可回滚且不改历史来源事实。
5. 人工 zh/en 名称/简介不被来源刷新覆盖；自动 profile 正确处理语言 fallback、来源过期与短期网络失败。采集失败或 Consumer reset/410 gap 不清空合法已发布作品；孤立的未绑定 Candidate 不进入正式游戏详情。

7. 既有 Site/D2 Start、年鉴、Logo、壁纸、热度、游戏原有 Public ID 和 URL 不变；不会因为 D3 修改旧站或 Harvest repo。版本化 forward migration 可重复执行、回滚业务决议不触发 FK 级联。

## 10. 结束条件与下一阶段

D3-A1 的终点不是“已经建了 Intake 表”，而是一个有效 Steam AppID 在受控范围内能通过 Harvest 完成自动预采集、身份归属和符合条件的自动公开，后续事实更新仍自动归属于同一 Game。没有可发布依据的游戏仍保留可自动补证据的记录，只有真正重要的关联问题需要人工。

下一阶段 **D3-A2 — Steam Metadata Projection & Discovery**：补全 Harvest 已采 Steam 字段的 GoFurry 规范化投影、Steam 增量候选发现，以及游戏类型/发行状态/搜索可见性模型。**D3-A3**：验证 itch.io 真实 Provider 的可行性。**D3-B/C**：游戏首页、目录、合集、详情、媒体、价格和玩家数据。**D4**：正式 Admin 自动运营界面。D5/D6/D7 遵守既定路线。
