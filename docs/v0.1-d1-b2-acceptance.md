# V0.1-D1-B2 — Site Yearbook acceptance

The Yearbook is keyed by immutable Site identity and UTC year. It reads GoFurry's compact evidence ledger and verified daily/monthly coverage. No Harvest process, credentials or public Internet acquisition are needed to generate or read it. Public APIs expose only a published revision; CN and INTL use their own databases.

## Evidence and operations

Algorithm version 1 closes a year on January 8 at 00:00 UTC. First publication requires a published Site, 14 distinct confirmed UTC dates spanning at least 28 inclusive days, and a verified baseline with an effective binding and matching coverage. Duplicate scopes do not add days. Missing dates remain Unknown. First-detected times belong to the evidence, and neither those dates nor the calendar establishes actual upgrade dates or availability. Year-end facts retain source host, scope vantage where recorded, ruleset, confidence, observation time and a durable opaque evidence reference; carry-forward is labeled. Domain moves preserve the Site identity and historical attribution.

Apply Goose explicitly to the intended regional database. Keep `yearbook.enabled: false` by default, or enable it in the regional API YAML after migration and review. The existing Fiber runtime runs a bounded check after start and daily thereafter, with at most 96 annual candidates per pass and one dedicated database connection. Ordinary public reads are independent of this setting. The operations below run from `services/api` with the same explicit YAML:

```sh
go run ./cmd/api --config /absolute/private.yaml yearbook preview PUBLIC_ID YEAR
go run ./cmd/api --config /absolute/private.yaml yearbook reconcile --dry-run --year YEAR
go run ./cmd/api --config /absolute/private.yaml yearbook reconcile --apply --site PUBLIC_ID --year YEAR
go run ./cmd/api --config /absolute/private.yaml yearbook publish PUBLIC_ID YEAR REVISION DIGEST
go run ./cmd/api --config /absolute/private.yaml yearbook hide PUBLIC_ID YEAR
go run ./cmd/api --config /absolute/private.yaml yearbook compact
go run ./cmd/api --config /absolute/private.yaml yearbook audit
```

Preview does not write. Reconciliation may publish an eligible first version; identical regeneration keeps its revision, and a correction is private until an operator selects the reviewed latest digest. Hiding preserves earlier published artifacts and removes the public route; already cached responses can persist for their cache lifetime. A published archived Site keeps its historical report until hidden. Public pages cache for 60 seconds; a 404/503 is not cached.

## Executed acceptance

- Disposable PostgreSQL **18.6**: B1 records and referenced rows survived the two forward migrations; a repeated Goose apply was a no-op. A simulated November 2026 and January 7, 2027 23:59:59 UTC could not publish 2026. At January 8 00:00 UTC two concurrent reconciliations produced one revision: fixture Site `0000000000000010`, **14/365** confirmed days (November 11–December 8), two domain transitions, and 351 unrecorded days. This is a partial year.
- The rollback fixture left no partial rollup. Compaction removed 27 old daily receipts while preserving the exact date masks and annual digest. A replay did not add days; a late confirmation produced a private second revision with 15 days. A stale digest failed; the reviewed revision survived reopening. Archive and hide preserved both historical published versions. Old binding/source removal and a Site name/slug change preserved historic attribution.
- Real PostgreSQL + built Fiber and Web (no Harvest): CN and INTL published a historical 2025 fixture from the optional job. Playwright exercised both default and alternate languages, canonical 301, no-record/future 404, public mutation denial, Site-only entry, dark/light, keyboard and a 320px reduced-motion viewport. Pausing the database produced 503 for Site and Yearbook while Start SSR remained 200; both recovered. Evidence and serialized HTML excluded raw HTML, sensitive DNS, URL parameters, internal IDs and secrets. Scoped withdrawal, ruleset-only changes, DNS TTL jitter, UTC boundaries and leap-day behavior were checked against PostgreSQL.
- The separate B1 regression uses the pinned Harvest D binary, two disposable PostgreSQL databases and simulated acquisition. It verifies snapshot/changes/ACK, 410 rebuild, restart/fault recovery and the preservation of prior Site facts. The annual service is deliberately absent from that acquisition path.

## Coverage storage and cost

The monthly table keeps one row per Site/binding/source/capability/schema/scope/month. A validated 31-bit mask preserves exact observed dates, with first/last confirmed instants and copied source attribution. The job keeps at least 45 days and waits for a month to be outside that window. It verifies the OR result and deletes only the matching locked daily records in the same transaction (2,048 per batch, up to 32,768 per call). Late verified receipts can be merged again. Unattributable rows are kept for the audit, never treated as coverage or silently deleted.

The measurement fixture uses 365 receipts per scope, one baseline and four material facts per Site. Heap includes TOAST/FSM; indexes include the B2 date scan index on the raw side. The rollup has 12 rows per scope and the comparison uses the same underlying evidence ledger. `VACUUM FULL` was used only on the disposable measurement database to compare reclaimable heap; the operational job does not run it or rewrite the raw table.

In the 100-Site, one-scope fixture, raw coverage occupied 26.1 MiB. The first compaction used 6.1 MiB of WAL and left 1.2 MiB of live-relation heap and indexes. The 1,000-Site, one-scope fixture used 198.4 MiB of raw coverage; the compaction added 32.3 MiB to the rollup relation and wrote 179.0 MiB of WAL. Including the unchanged evidence ledger, the observed physical footprint was smaller by 93.6% and 82.0% respectively. The first generated snapshot was 2,402 bytes; its database-backed public lookup averaged about 0.9 ms in both samples.

## Integrity and boundaries

B1 had **17** foreign keys with RESTRICT/NO ACTION and no cascade. B2 removes those ties from long-lived coverage/facts and replaceable collection state. Typed ownership checks at the write/read boundaries, unique keys, explicit retirement and the read-only `yearbook audit` protect consistency; a deliberately misattributed daily row was detected. B2 adds **zero** foreign keys or cascades. D1-A's four Site/Game localization/address/source links are retained because these rows are editable children with no valid independent lifetime: the constraints reject orphan inserts and parent deletion even through direct database maintenance outside application transactions. Neither historical migration was changed.

No shared development database was reset; no production database, public Steam/Web collection or real 2026 publication was exercised. Once compacted, individual receipt times cannot be recovered beyond the stored minimum and maximum; the date set and provenance are retained. On very large backlogs, use the bounded `compact` command repeatedly and audit unmatched historical rows separately. No Start, preferences, theme, wallpaper, search, weather or global styling source was changed.
