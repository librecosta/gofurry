本阶段冻结 D5-B1 的兼容目标、身份和重放规则。生产数据验收仍待执行。字段逐项归属、实际 Seed v1 文件和目标写入条件见 [Source-to-Target 字段映射](v0.1-d5-b0-field-mapping.md)。

## 1. 目标和已知模型缺口

Catalog 继续拥有 Site、Game、合集和编辑决策。导航只使用已有固定词表。Steam 资料仍按 `GameSource`、语言、商店地区和出处归属 Harvest 投影。D5-B1 消费 D5-A 的离线目录，使用 CN 隔离环境和正常 Catalog 写入语义。D5-C 负责真实批次的部署与验收，D6 负责 CN→INTL 投影。

| 能力 | 基线事实 | D5-B1 的最小补齐 |
| --- | --- | --- |
| 旧身份和导入回执 | D1 已约定 `legacy_site_ids`、`legacy_game_ids`，当前 migrations 尚未创建。D4 的 `management_operations` 记录受保护 HTTP 请求结果。 | 实现 D1 的两张映射、其他实体的有限类型映射以及私有批次和逐单元回执。导入回执独立于 HTTP 请求回执。 |
| 游戏人工标签 | 现有 `genres` 读自 `game_channel_steam`，人工标签类别、标签、游戏关联没有目标表。 | 新增 Game 专用人工类别、标签和关联。保留双语、排序、归档和 `normal/primary/secondary`。 |

| 旧分组、日期与任意文本附件 | Site 固定词表没有旧分组对象或组内权重。Game 详情的开发商、发行商与发行证据来自平台，现有模型没有这些字段的独立人工层。 | 有目标语义的内容按矩阵写入。其余保存在私有证据包及定位回执，由真实数据决定是否另行扩展。 |
| 旧精选、历史地址、Logo | Site 与合集各有三个固定精选槽。Site 已有主备地址、不可变 Logo 键及 revision 绑定。 | 旧精选和历史地址保留出处，地址和 Logo 只在核准后绑定。 |

## 2. 输入与核准计划

1. **Seed。** 输入为私有 D5-A `schema_version=1` 目录、独立登记的备份 SHA256 和内容 SHA256。复用 D5-A 的离线校验规则与解析器，核验 `manifest.json`、`SHA256SUMS`、文件白名单、UTF-8、大小和行数、严格类型与排序、引用与异常对账、所有 `ready` Logo 实际字节。覆盖附件中实际存在的 `game_release_candidates.ndjson` 和 `excluded-release-rows.ndjson`。`ready_for_D5_B` 只表示 D5-A 包完整，`asset_complete=false` 可进入内容计划，所有缺件仍列出。固定只读视图或私有不可变工作副本，apply 前再次验证输入摘要。哈希验证字节完整性，归档来源由独立登记和核准确认。
2. **规则和决议。** 使用显式私有配置和严格版本化的决议文件。冻结 `decision_schema_version=1`，每条与 Seed 内容哈希、源主键或明确的源键集合绑定。每条以 `operation + subject` 去重。`subject` 是类型化源键或已列出源键的有限批次组。允许的操作为 `map_group`、`supply_slug`、`select_address`、`select_source`、`link_existing`、`alias_existing`、`resolve_tag_code`、`resolve_relation`、`allow_logo` 和 `allow_publish`。操作值使用各自的类型结构，包含预期角色或动作和拟采用的规范值。地址、平台、别名、素材和发布均逐类核准，可复用同一经批准的批次证据策略。每条有可核对的证据引用、原因和负责人。内容分级与既有来源纠错沿用 D4 的 Owner 权限边界。已有目标需载明实体类型、UUID、Public ID 和预期 revision。重复或相互矛盾的决议、未知规则/字段、悬空引用使计划失败。旧站账号和审计正文属于排除项。CLI 用真实执行身份与 `legacy_import` 系统归因，保留批准凭据引用。D4 路径继续使用服务侧认证的 Actor。
3. **计划。** `legacy-import plan` 读取 Seed 和隔离的目标 PostgreSQL，只读目标快照，输出规范化逐单元方案与预计差异、冲突、依赖和资产清单。计划不创建身份。新对象以类型化源键引用。`plan_sha256` 覆盖源部署、备份和内容摘要、目标部署/数据库标识、迁移模型版本、映射规则版本、决议摘要、预期 revision、排序后的单元意图及字节哈希。输出路径、测量时间和执行日志不进入内容摘要。`apply` 接受精确摘要并重新校验计划。`verify` 对照目标数据库和回执重新读取，不执行写入。
4. **隔离。** B1 验收仅允许显式启用的 CN disposable PG18。校验目标部署环境、连接端点、库名和预置测试标识，存储配置另行绑定隔离 Bucket 与 CDN 模拟入口。名称与回环地址不能单独证明隔离。源库凭据、旧站地址和旧 Bucket 不进入导入运行配置。Goose 使用显式前向迁移，版本差异在写入前报错。

## 3. Identity / Conflict / Idempotency

### 旧键、目标身份和链接

| 源实体 | 稳定源键 | 目标 |
| --- | --- | --- |
| Site | `(legacy_deployment, site, gfn_site.id)` | `legacy_site_ids → sites.id` |
| Game | `(legacy_deployment, game, gfg_game.id)` | `legacy_game_ids → games.id` |
| Game Collection | `(legacy_deployment, game_collection, gfg_game_collection.id)` | 有限类型映射 → `game_collections.id` |
| Game Editorial Tag Category | `(legacy_deployment, game_tag_category, gfg_tag_category.id)` | 有限类型映射 → 游戏人工标签类别 UUIDv7 |
| Game Editorial Tag | `(legacy_deployment, game_tag, gfg_tag.id)` | 有限类型映射 → 游戏人工标签 UUIDv7 |

- 本轮唯一旧部署标识为 `gofurry_nav_site_cn`，与运行目录名、`snapshot_id`、备份哈希和 `gfn/gfg` 的临时数据库名称无关。每类 ID 独立，源键必须是正的 PostgreSQL `bigint`。关系用整个 `source.key` 和表名定位，不能用只取首项的 `legacy_id`。同部署不同快照复用映射。区域数据库隔离，B1 只从此旧部署写入隔离 CN。D6 将来投影获批的同一内容时沿用 CN 的 Public ID 和 canonical slug，各地区可以使用不同内部 UUID。
- Site/Game 遵循 D1 的独立映射表和限制性 UUID 外键。其余三类可共用有限类型的迁移映射，由各自目标表和锁定校验约束。稳定映射至少存旧键、目标 UUID、首次批次和决议引用，核验信息包括核验状态、时刻、可验证的核验人。回执可记录指向当前目标的 Public ID 供核对，权威值从目标表读取。
- 新 Site/Game/合集复用 Go 原生 `uuid.NewV7()` 和 Catalog 独立的 16 位小写 Base32 随机 Public ID（80 位随机量）。使用目标唯一约束和有界碰撞重试，成功写实体、映射和回执才分配完成。标签类别与标签只分配内部 UUIDv7。Public ID 保留到归档和恢复，slug 可变、可重复。初始 slug 依现有规范从安全的英文或 ASCII 资料得出。缺可用 slug 时由计划提供合法值，也可明确为该类统一的装饰性默认 slug。原数字 ID、AppID、域名和翻译均不参与 Public ID 生成。
- 同一旧键一旦映射，导入器只核验该目标。目标缺失、类型或 Public ID 改变，停止该单元并升级为完整性冲突。基于审核决定采用已有目标时，只建立映射并核验当前目标。允许 Site/Game 多个旧键指向同一目标的唯一入口是显式 `alias_existing`，须逐一记录语义和审核证据。已有映射改指向、合并或拆分已有实体由独立纠错处理。
- 裸十进制 URL 仍按 D1 由将来的已审核数字映射处理。导入映射不激活路由。历史域名、旧探测 URL 和当前外链属于 Site 地址证据，不能生成站内数字重定向、关联合并或站外自动 301。

### 重放、并发、人工保护

| 情形 | 处理 |
| --- | --- |
| 同计划、同单元已提交 | 比对已提交回执和身份。读回差异作为既有人工修改报告，重放不改 revision、时间、字段、状态或外部资源。 |
| 超时或连接断开，提交结果未知 | 先用批次、单元键和意图摘要读取回执。有回执按已提交核验，无回执且身份/计划仍适用才重试。 |
| 相同旧键、新快照或新决议 | 新计划绑定新的输入摘要，重新对账。已完成单元仅核验和比较。实体已建立但尚未完成的后续阶段可按新计划继续，须匹配原映射、预期 revision 和所写字段的基线。 |
| 未映射但存在同名、同 slug、同域名或同 AppID 的记录 | 作为匹配证据报告。强外部键冲突阻止该 Game 的身份/来源写入，由审核决定认领已有目标、选择可证不同的来源，或解除该来源候选。名称和域名相同不自动合并。 |
| 已有编辑、空白覆盖、主备地址变动、下架或来源撤销 | 已有实体采用 map-only。迁移创建对象按阶段使用目标锁和 CAS。计划外的 revision 或规范化前像变化标为 `editorial_conflict`，保留当前值。D4 继续负责既有实体的发布纠错、来源迁移和人工作品改写。 |
| 非法 ID、孤儿、冲突字段或超过目标容量 | 可用字段按矩阵导入，缺陷字段或依赖单元进入待决，并保留源定位。需要原子保存的关系集合没有通过校验时整体等待决议。超限不能靠静默截断解决。 |

稳定的回执单元键由 `target_deployment + batch(plan_sha256) + phase + source_table + source_key` 决定。成组的标签关联和合集关系以父实体键作为提交定位，每条子来源在回执中仍须可核对。记录意图摘要、结果、目标身份、已提交 revision、映射/策略版本与时间。Logo 对象阶段另以 `target_store + SHA256` 标识远端对象。导入批次锁按目标部署和旧部署取得，数据库约束和现有领域行锁继续约束与 D4、Intake 的并发。域内写入复用同一 sqlc/pgx 事务。禁止借由全量替换子表覆盖管理端的变化。

## 4. Editorial 语义

### 导航与发布

- Site 将已核准的组映射到固定词表。单站显式决议优先。其余采用已核准的分组映射，依源 `priority ASC, group_id ASC` 选主类及补类，经规范化去重后最多一主两补。未映射和超出槽位的来源关系继续保留对账定位。组内 `weight` 只能用于该旧组排序证据。它没有跨组分类优先级或 Heat 含义。缺分类、Logo 或新采集事实不制造发布门槛。
- 地址决议指向一个具体的源候选和审核证据，明确 `primary` 或 `alternate`。入库复用目标 URL 验证器，并保留 D5-A 对旧候选的更窄边界。`proposed_url`、`basis=explicit`、开放区间或合法协议都不能独立证明当前地址。历史已关闭、协议未知、归属冲突等地址留作私有证据。允许相同主机服务不同 Site，分别核验其业务 URL。已存在的自定义 Site 地址留给 D4 维护。
- 新目标默认 `draft`。旧 Site 明确软删按可核验状态进入归档，真实旧归档时间和理由保留为来源证据。旧 Site `nsfw='1'` 保留成人边界，绑定到现有 Site 分级和审计。`nsfw='0'` 只有在真实旧资产说明、标记来源和版本化的批次政策表明可继承时才提供正面证据。其余保持 `unreviewed`。D2 迁移产生的 `legacy_detail` 只对应已有新版历史，不能作为本次导入的公开资格。
- 新 Game 从人工 `game_localizations` 读取，保留 `intake_managed=false`。命中旧 `adult` 证据的新 Game 使用既有 `publication_blocked` 与决策记录。`not_flagged_adult`、曾可见、旧分类或有效 AppID 都不足以认定 SFW。Unknown 可入草稿，无采集数据、跨平台来源或封面也可入草稿。
- 发布是计划中显式独立阶段，只处理该批新建对象，按现有 Catalog 校验和 R1 的持久性规则执行。Site 要求可发布 locale、核准 SFW 和唯一主地址。Game 要求可发布 locale、可归属的正面 SFW 证据及既有发布条件。合集要求完整核准的关系集合和可发布文案。继承规则可按证据批量批准，真实疑难才交人工。采集或 Logo 失败不撤回已有合法发布。目标首次发布时间只记录目标真正发布的动作，源时间保存在来源证据中。

### GameSource

- 对无重复、无矛盾的 D5-A `steam_appid`，可在一个新 Game 的创建事务内写入 `steam` 来源。键用 uint32 正整数的规范十进制，URL 固定 `https://store.steampowered.com/app/<appid>/`。同一个有效 Steam 候选与一致的商店链接只落一条。纯链接线索、多个 AppID、旧 AppID 和商店链接矛盾，保留证据并进入决议。
- itch.io 必须有核准的作品级证据。复用 `itch_io` 和小写 `creator/game` 规范（创作者 ≤63、作品 ≤80，canonical URL 为 `https://<creator>.itch.io/<game>`）。同名、作者相同、RSS GUID 或链接可访问都不证明它与另一个平台是同一作品。域名或 slug 迁移不等于更换内部 Game。演示、DLC、本体或合集需确认作品边界。不做跨平台身份推断。
- 唯一键 `(platform_code, external_key)` 包含停用来源。已有同一 Game、同一规范键、URL 一致且 active 时为核验无操作。停用、已有不同 URL、其它持有人或旧规范化 itch 键多条命中均列为冲突。不会重新激活、重签归属或复制为新来源。新的多来源只写给本次创建对象且每项经明确确认，遵守现有最多 16 条活跃来源。并发与 Intake/管理写入通过目标唯一约束和事务复核收敛。预检后若其他写入方抢先占有任一来源，回滚该 Game 的创建和映射，保留原持有人。不能使用会将现有来源隐式激活的更新路径。Harvest 绑定和排程由既有流程独立操作。
- 不能将社区/资源链接、人工开发商发行商或发行日期填入 `game_sources` 或 Steam 观测。价格、人数、新闻、Genre、媒体等继续使用可信平台投影。

### 人工标签与合集

- 新的游戏人工标签类别与标签使用稳定 UUIDv7、受控代码和 zh/en 文案，归档保留原 ID。类别代码在类别命名空间唯一，标签代码在人工标签命名空间唯一。有效旧代码原样采用。重复或无效代码由显式决议提供修正，保留旧代码证据。新映射保留类别排序值和 `game/tag` 的 `normal/primary/secondary`。同一 Game/Tag 只能有一条关系，同一 Game 至多一个主标签和一个次标签。归档类别下的关系保留，暂停自动命中。旧 `adult` 命中独立用于既有内容边界。公开 Genre 契约继续取 Steam Genre。
- 现有 `game_collection_members` 保存人工固定成员。优先使用显式核准的完整排序，否则使用稳定的 `export_order, legacy_game_id`，压成 `position=1..N`。`export_order` 是迁移排序依据。导入报告明确它的来源。超过 512 项或存在未决孤儿时，合集的人工成员、规则、排除一起暂停写入。可先保留非公开的合集身份和文案。最终解决集须重新校验容量，保留每条未采用关系的原因。
- 新增两种窄关系 `(collection_id, tag_id)` 和 `(collection_id, game_id)` 存标签规则和显式排除。有效成员为 **（人工成员 ∪ 命中任一未归档 Tag 且其类别未归档的成员）− 显式排除**。三种角色可命中。命中多条规则只计一次。固定与排除并存保留两条且排除优先。稳定编辑顺序先按人工位置，再按自动成员 Public ID。发行时间线继续用现有可信发行数据和未知排序。
- 公开详情和合集相关推荐使用同一有效成员定义，再应用 `game_channel_public`、合集状态和既有分页规则。管理端原来返回的人工成员列表维持原义。规则、排除、标签归档或关联变化使有效成员可能改变时，同事务更新受影响合集 revision，让既有游标校验失效而不是跨版本漏行或重复。写入固定锁顺序和幂等键。带条件索引和有界分页，避免把自动成员复制为人工行。

## 5. Site Logo 交付顺序

1. 对每个 `ready` 引用查到对应已解析的 Site 旧键与 `assets/site-logos/<sha256>.webp`。索引中的路径、`output_sha256`、字节数、宽高与 manifest 必须吻合。复用 `storage.SiteLogo` preflight 验证相同字节的静态 WebP、最大 1024×1024 正方形、1 MiB 和完整解码。未通过则报告，保留已有 Logo 和文字资料。
2. 只为核准 Logo 在配置的目标 Bucket 上传一次。目标键由字节 SHA256 得出 `sites/logos/<64 lowercase hex>.webp`。用已有 `If-None-Match: *` 不可变写入。超时和已存在均靠 `VerifySiteAsset` 核对 HEAD、SHA256、下载解码和配置 CDN 的公开响应。内容类型不符、旧对象与同键内容不一致或 CDN 交付失败均保持待处理，禁止覆盖。
3. Site 身份和文本可以先提交。对象验证完成后，用短事务锁定新建 Site，核验其映射、当前 Logo 值和预期 revision，绑定验证过的键并记录回执。已有同键且一致为无操作。已设置别的键、已被人清除或目标已变化时保留当前值。此前未有引用且源状态缺失时保持空值。禁止由 Seed 缺件去解绑现有 Logo。
4. 对象写成功但 DB 事务失败时，对象可能存在而无引用。重跑先复验同键并绑定，未被引用的对象只在私有报告列出。回滚不会删除共享内容寻址对象。绑定失败也不会修改其它 Site 或对象。这条链只接收 Site Logo。

## 6. D5-B1 执行、对账与回滚

| 阶段 | 提交单元与失败处理 |
| --- | --- |
| 预检 | 校验 Seed、决议、计划哈希与隔离目标。记录批次和模型版本。无有效写入许可、输入篡改或错库时整批停止。 |
| 身份及资料 | 每个 Site/Game/人工类别/标签/合集头一个短事务，解析权威旧键，在同一事务内写目标、映射、支持的初始编辑字段、策略或归档意图以及回执。Site/Game/合集头先以私有草稿创建。Game 来源归属和 Site 已核准地址随实体原子提交。锁冲突或第二阶段引用缺失进入可重试或业务待决。 |
| 关系 | 每个 Game 的人工标签集、每个合集的完整人工成员/标签规则/排除集，各按一个事务提交。固定顺序复核依赖和预期 revision。待决关系阻止该集合的提交，已提交的其它集合可重放核验。采用既有 Game 或合集时仍按 map-only。已确认的旧关系可以令新合集引用既有 Game，保持被引用 Game 的数据和 revision。 |
| 资产、归档及发布 | 外部对象写入独立在事务外。用短事务核验并绑定 Logo。拟归档 Site 先在草稿尝试绑定，缺件或上传失败仍可按计划归档并留资产待决，重跑不会为了 Logo 解开归档。显式归档或发布阶段按相同身份和 revision 校验。本批新建对象的后续阶段以最近的已提交回执取得预期 revision。历史归档没有新版发布时间时保留空值。 |
| 验证 | 重新从 DB 核对映射唯一性、目标 UUIDv7/Public ID、locale、状态/审计、源归属、规则结果、支持关系和 Logo 引用。核验原有实体的 preimage 和 revision，区分合法的并发人工修改。核对数量、摘要和真实差异后才结案。 |

每个源主键最终只有一个对账状态。`source_rows = applied + verified_existing + evidence_only + deferred + conflict + excluded_upstream + retry_pending`。创建与关联是 `applied` 的子计数。逐字段降级、多条来源映射到同目标以及 Logo 去重另列，不能用目标行数替代源计数。核对 D5-A 逐表 `exported_usable + exported_unresolved + explicitly_excluded`，合并文件按真实 `source.table` 分开。对账包括每集合的人工、规则、排除、交集和公开有效数，以及 Logo 引用数、唯一对象数、上传/复用/验证/绑定/缺件数。

详细报告按 `source.table + source.key + field + phase` 定位，含 `issue_code`、是否可重试、决议引用、计划/批次摘要、目标 scope/ID/revision、实际结果。归档私有 Seed、决议、计划、回执和证据定位。可分享报告仅含行数、置信边界和固定异常代码。连接信息、URL、旧对象键、凭据、用户资料和全量源行不进日志或 CI 成品。

事务报错回滚本单元的映射、目标变更、审核和回执。进程崩溃后按已提交回执恢复。批次可能部分完成，报告保留已写、未写和待验子集。撤回已经提交的计划通过带预期 revision 的补偿动作和审计完成，保护有人编辑的目标、Public ID、旧映射及共享对象。D5-B1 验收可直接丢弃一次性隔离环境。校验失败、回执不全或目标漂移时不给出“已完成”结果。
