## Empty suggestions: actual cause

The private CN YAML already enabled suggestions and selected a working explicit
proxy. DuckDuckGo returned eight phrases for each of `furry`, `兽人` and `GoFurry`.
The CN exact-match list contained only eight golang-related phrases, so its
intersection with those results was empty. Code also disabled CN when no list
was present, applied an unapproved keyword blacklist in both regions, and hid
upstream failures behind successful empty arrays. The example default was false.

Those restrictions are removed. Omitted `search_suggestions.enabled` now means
true in either region; explicit false disables the whole feature. Remove the
obsolete `cn_allowlist` from existing private YAML: unknown fields still fail
validation. The root development YAML was migrated without committing it.
Queries/suggestions are separate from the site's own SFW content policy.

Both deployments use the same DuckDuckGo `/ac/` request/JSON v2 parsing and the
same default catalog platform, Bing. Manual Google/DuckDuckGo selection and
platform-independent suggestions remain. No platform was added or removed.
The old provider's explicit proxy, JSON phrase format, cancellation and frontend
interaction were compared read-only; no old service is used.

The development network cannot reach DuckDuckGo directly (bounded connection
timeout); its existing explicit YAML proxy succeeds. Go never consults system
HTTP_PROXY/HTTPS_PROXY. Transient proxy/upstream timeouts also occurred during
acceptance and were returned as 503/timeout, not a fabricated successful `[]`.
Subsequent genuine requests and both regional browser runs passed.

## Contract and operational diagnostics

- Success: 200 `{ "suggestions": [...] }`, with
  `X-GoFurry-Suggestions-State: ready|empty`. Empty is a real successful empty
  upstream result or an empty query, never a disguised transport failure.
- Invalid input: 400/invalid_query. Explicit disable: 503/disabled. Saturation:
  429/busy with Retry-After. Upstream failures: 503 with bounded network, timeout,
  upstream_http, response_body, response_size or invalid_response state.
- Errors retain the existing unified error/request-ID envelope and Region/SFW
  headers. Logs include only state, numeric upstream status and request ID, not
  keywords, raw errors, addresses or credentials. The Web relay forwards the
  diagnostic header; the UI still quietly closes on failure.
- Limits remain 128 Unicode characters, valid UTF-8/no control or format
  characters, 64KiB upstream body, three-second HTTP timeout, eight deduplicated
  results and four local merged-key flights. Frontend 600ms debounce, IME,
  AbortController/generation checks, keyboard selection and empty/error dismissal
  remain unchanged.

## Existing Redis integration

`redis.address`, optional ACL `username`, `password` (may be empty) and `db` come
only from the single Go YAML. The existing development Redis required its ACL
user; its connection values were migrated locally from the old private file,
without displaying credentials or modifying that repository. One go-redis/v9
9.23.0 client belongs to startup/shutdown; no new cache service is deployed.

Keys use deployment/domain prefixes and SHA-256 input digests. Suggestions cache
256 entries for ten minutes, with an absolute expiry also respected by local
hits. Weather caches 512 entries, retains original `fetched_at`, is Fresh for
under 20 minutes and Stale only below 60 minutes; Redis TTL is the remaining age
budget. Domain indexes evict only their own bounded keys. No IP-to-weather cache
exists. Short ownership-checked leases merge cross-process cold misses; weather
failure cooling is shared. Existing local merging and provider bounds remain.

Shared fixed-window quotas are suggestions 240 global/60 client and weather
120 global/20 client per minute. The existing official Fiber local quotas stay
in front, including during Redis outages. Rate keys hash the resolved client IP
and expire after 60 seconds. The Web relay still shares its source-IP budget;
untrusted forwarded headers are not accepted. Redis operations have 250ms
deadlines and no automatic retries; missing/unavailable Redis uses local fallback
without taking down unrelated API routes. No periodic jobs or generic cache
framework were introduced.
