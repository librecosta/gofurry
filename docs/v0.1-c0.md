## Decision and implementation

Keep Base UI **Popover, Menu, Dialog, Tabs and RadioGroup/Radio**. B was stable and C provided no observed improvement, so replacing keyboard/focus/positioning behavior would add work without evidence of benefit. Base UI has no visual animation ownership. Use the [official Motion composition](https://base-ui.com/react/handbook/animation#animating-components-unmounted-from-dom-when-closed-with-motion): controlled roots, `AnimatePresence`, `Portal keepMounted`, `Popup render={<motion.div ... />}`. Popup opacity/translation starts with its Motion element, exits remain mounted, and CSS starting/ending animation selectors are absent. Static dialog centering uses CSS `translate`, separate from Motion's transform.

- `styles/tokens.scss` holds the existing palette and Dark overrides, including search material roles. `themes.scss` exposes inherited semantic CSS properties and resolves system colors before JavaScript. `global.scss?url` links reset/fonts/themes in the root document. Other rules live in CSS Modules, including the diagnostic routes.
- Motion 14.9.0 owns 420ms popup/search-panel lifetimes, 400ms Tab/segment movement, 300ms radio/hover opacity and 480ms background fades. A single search panel remains inert during exit and reuses its DOM for platform/suggestion changes; manual animation timeouts/double-rAF mounting were removed. Simple color states and immediate focus feedback stay in SCSS. Reduced-motion resolves Motion durations to zero.
- The native circular theme View Transition remains unchanged. Region, language URLs, cookies, provider selection, suggestion cancellation/IME, background metadata/decode logic and the API remain unchanged.
- StyleX dependencies, plugin, virtual CSS, DevStyleX, declarations, runtime imports/props and replaced files were removed. No Tailwind or parallel styling system was introduced. Sass 1.107.1 is pinned; pnpm explicitly denies the optional watcher's build script while using packaged bindings.

## C4 follow-up: popup text, not popup layout

A later cold-cache Chrome check distinguished font loading from the original geometry report. With quick access enabled, the Chinese platform dropdown first fetched Noto Sans SC subsets 105 (`哔/哩`) and 113 (`乎`). The Logo also fetched 113 for its hidden `暂不可用` description; its visible navigation text and the User menu already used the final font. Deliberately holding subset 105 reproduced a visible FOUT: CDP `CSS.getPlatformFontsForNode` reported four Microsoft YaHei UI glyphs in `哔哩哔哩`, then four custom Noto Sans SC Medium glyphs after release. This is a controlled slow-font reproduction, not a measured normal-network delay.

Chinese Start URLs now SSR-preload only those two existing, same-origin WOFF2 assets (~120 KB total); English does not preload unused Chinese menu subsets. No font stack/weight, popup positioning, animation or page visibility delay was changed. Cold first/repeated opens in Dev and the local production build had no late font requests or rendered-font/weight/width substitutions. The retained 420ms opacity/4px movement still changes text blending during entry; that is not a font-family swap. No visible Logo/User FOUT or positioning jump was reproduced, so neither was replaced on speculation. At rest, Chrome screenshots with `transform: none`, identity 2D and identity 3D transforms were pixel-identical; adding a permanent GPU-layer workaround had no demonstrated benefit.

The focused font check in `tests/start.spec.ts` records actual rendered fonts, CSS metrics and first/repeated open screenshots in both languages. Ignored local diagnostics are in `bin/c4/` (`visible-font-swap.json`, fallback/loaded screenshots and raster comparisons). SCSS HMR can use `PLAYWRIGHT_HMR_PORT=17324 task check:hmr` to avoid stopping a user's existing development listener; its default remains 17320.
